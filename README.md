# 微购 App 原型与设计系统

一个由 AI 工作流驱动的**中文移动端交互原型仓库**：你只需要用自然语言描述业务需求，仓库内置的 AI 技能就会完成需求确认、页面设计、交互实现和验证，产出可以在手机预览壳里操作的交互原型。

全程以 **Codex、Trae 等 AI 编程工具**为操作入口：你负责描述需求和确认结果，环境准备、代码修改、验证、提交和 PR 都由 AI 代劳。

[查看正式线上原型](https://zhoujieh.github.io/wego-design-system/)

---

## 快速开始：打开你的 AI 工具，跟着这 5 步走

下面每一步都只需要你**在对话框里粘贴指令**，剩下的交给 AI。遇到任何阻塞，让 AI 停下来告诉你，不要让它跳过。

### 第 1 步：打开仓库

用 Codex / Trae（或任何支持 Git 仓库的 AI 工具）打开这个项目：

- **如果本地还没有仓库**：让 AI 执行 `git clone https://github.com/zhoujieh/wego-design-system.git`，然后在工具里打开克隆下来的目录。
- **如果已经有了**：在工具里直接打开仓库目录，让 AI 执行 `git pull --rebase origin main` 更新到最新。

### 第 2 步：让 AI 准备环境

把下面这段整段复制、粘贴给 AI，它会自动完成环境检查和准备（除了 GitHub 协作者邀请邮件需要你自己点接受之外，不需要你敲任何命令）：

> 你是这个仓库（wego-design-system）的 GitHub 协作者。请帮我把本地环境全部准备好，让我能开始给仓库里的 AI 技能发业务需求、做交互原型。除了「接受 GitHub 协作者邀请邮件」这一步必须我自己点邮件接受之外，其余全部由你完成，我不需要自己敲命令。
>
> 请按顺序做，每步遇到阻塞就停下来告诉我，不要跳过：
>
> 1. 检查环境：确认已安装 Git 和 Node.js（要求 >=18，建议 20+）。缺哪个就告诉我具体安装方式（不要自动改系统配置，除非我同意）。
> 2. 复制仓库：如果本地还没有这个仓库，执行 `git clone https://github.com/zhoujieh/wego-design-system.git` 并 `cd` 进去；如果已有，执行 `git pull --rebase origin main` 更新到最新 main。
> 3. 安装依赖：执行 `npm install`（仓库唯一的开发依赖是 playwright）。
> 4. 安装浏览器：执行 `npx playwright install`，确保自动化验证能跑。如果已装过就跳过。
> 5. 校验：跑一次 `node scripts/validate-wego-design.mjs --scope=changed --strict`，确认环境没问题；有任何报错把关键信息贴给我。
> 6. 预览：帮我从仓库根目录启动仅绑定 `127.0.0.1` 的本地预览服务，并告诉我可点击的 `http://127.0.0.1:<端口>/wego-app/` 地址。环境初始化预览不进入任务验收，确认环境正常后由你关闭服务，避免遗留进程。
> 7. 准备就绪后，告诉我「环境已就绪，可以开始发业务需求了」。

注意：不要改动 `wego-app/lib/` 和 `components.css`（设计系统只读消费）；不要直接提交 main；不要执行 `git add -A`。

### 第 3 步：发第一个需求

环境就绪后，用自然语言把业务需求说清楚。参考下方「需求怎么写更好」的四要素，例如：

> 我想要一个「订单查询」功能：从首页的订单入口进入，用户输入订单号点查询，能看到订单的状态（成功 / 失败 / 找不到），失败时给出提示并允许重试。

AI 会先和你**澄清需求细节并生成需求简报**，你确认简报后，它才开始设计页面。

### 第 4 步：本地迭代看效果

需求确认后，AI 会自动创建功能分支和本地预览，改一版你就看一版。这个阶段默认只更新本地预览，**不会**自动推送、创建 PR 或刷新线上。你只需要看效果、提反馈（"继续""再调整一下"都可以），AI 持续修改。

### 第 5 步：正式验收

当你觉得这轮改完了，**明确说一句"提交验收"（或"创建/更新 PR""发在线预览"）**，AI 才会集中提交代码、跑完整验证、创建或更新 PR，并给你两个验收链接：

- 本地 HTTP 预览（仅绑定 127.0.0.1）
- PR 在线预览：`https://zhoujieh.github.io/wego-design-system/previews/pr-{PR编号}/`

你在真机上验收通过后，AI 才会合并到 `main` 并更新正式线上原型。注意：普通反馈（"改好了""继续"）**不会**触发提交和 PR。

## 给 AI 的需求怎么写更好

说清下面四点，AI 就能直接开工，不用反复问你：

- **入口在哪**（从哪个页面进来）
- **用户首要任务是什么**
- **主要操作**（点什么、选什么）
- **能看到的结果和必要状态**（成功 / 失败 / 空态等）

参考图、线框图、Figma 只作为视觉方向，**不能替代你确认过的需求简报**。

## 本地迭代与正式验收（两个阶段）

每个任务分成两个阶段，AI 会明确告诉你当前处于哪个阶段：

- **本地迭代中（默认）**：AI 创建或复用功能分支和 worktree，持续修改并更新本地 HTTP 预览；不会自动推送、创建 PR、等待 Actions 或刷新在线预览。适合连续处理多个小问题。
- **正式验收中**：只有你明确要求"提交""推送""创建/更新 PR""发在线预览"，或说明"这一轮改完了，可以验收"时，AI 才集中提交、推送并创建或更新同一个 PR。

业务原型正式验收同时提供本地 HTTP 和 PR 在线两个链接；设计系统组件、Token、Preview 或 UI Kit 只使用本地 HTTP 预览。每次结果都会标明当前处于"本地迭代中（未推送）"还是"正式验收中（PR #编号）"。

## 多人协作要点（给想知道的人）

- 各人开 `feature/<你>-<场景>` 分支，不要直接提交 `main`。
- 每次开工前先 `git pull --rebase origin main` 基于最新代码。
- 开工前在 `claims/<你>.json` 认领场景、记录当前 `branch`，并跑 `node scripts/validate-claims.mjs`，避免两人改同一场景；CI 会核对场景变更与分支认领一致。
- 一个交付单元固定一个功能分支和 worktree；首次开始任务不自动创建 PR。
- 本地迭代期间只更新当前 worktree 的本地预览。确有多人远端协调需要时，可以只推送最小认领提交暴露分支，但不创建 PR、不进入正式验收。
- 获得明确提交授权后，集中提交并推送当前分支，创建或更新同一个 PR。
- 业务原型正式交付同时获得两个验收链接：当前 PR 分支 worktree 的本地 HTTP 预览，以及 `https://zhoujieh.github.io/wego-design-system/previews/pr-{PR编号}/` 在线预览；两个链接进入同一场景入口。
- 设计系统组件、Token、Preview 或 UI Kit 维护只提供本地 HTTP 预览，不以 GitHub Pages 作为验收入口。
- 本地预览服务在本地迭代和等待验收期间保持运行；用户验收通过、任务废弃、PR 关闭或合并、对应 worktree 即将清理时，由 AI 停止服务并清理记录。
- PR 更新后原在线验收链接自动更新；用户明确验收通过后才合并到 `main`。
- 正式线上原型只展示已经验收并合并的稳定内容。
- 完整协作约定见 [`AGENTS.md`](AGENTS.md)；脚本与验证命令见 [`scripts/README.md`](scripts/README.md)。

> 普通设计任务把设计系统当**只读**用，不要改 `wego-app/lib/` 和 `components.css`；只有做设计系统维护任务才改源。
