微购工作流核心流程梳理

依据仓库权威文件梳理：AGENTS.md、.codex/skills/README.md 及各技能 SKILL.md / references / experience ｜ 整理日期：2026-09-03 ｜ 面向：微购用户体验设计中心

一、工作流全景

微购是一个「AI 工作流驱动的中文移动端交互原型仓库」：业务原型固定经过 需求确认 → 本地设计迭代 → 自动验证 → 用户验收 这条链路，精简文档或守卫不得绕过。四种技能按用户意图路由，其中三条是业务主链路，交付技能负责分支 / PR / 预览 / 合并支撑。

1. 技能路由表

用户意图技能核心职责
新业务需求、页面、流程或业务范围变化wego-product创建迭代并确认 prototype_brief（需求规格说明是唯一需求源）
已确认范围内的页面设计与实现wego-design消费设计系统，产出可交互 App 场景；不定义业务需求、不改设计系统本体
组件、Token、Preview、UI Kit、消费规则、守卫或工作流维护wego-uxsystem-iterate唯一权威源维护；经验沉淀与工作流迭代
分支、PR、本地迭代预览、合并或交付分支清理wego-github-delivery交付单元核对、worktree、PR、预览服务、合并收口

2. 主链路一句话

需求（自然语言/参考图/Figma）→ 启动清单→ wego-product 简报确认→ wego-design 本地迭代→ 自动推送同一 PR→ 用户明确验收？→ 固化+完整验证+合并 main
  • 输入形态一律先走产品技能：无论自然语言、参考图还是 Figma，都视为业务需求，必须先创建迭代并确认 prototype_brief 才能进入设计实现；Figma / 参考图不用于补造业务事实。
  • 已确认简报即设计授权：范围内信息分组、布局、组件、Token、反馈和 overlay 由 wego-design 自主完成，不建立第二次确认门禁。
  • 合并必须用户明确验收通过：普通反馈（改好了 / 继续 / 再调整）不构成验收授权；实现完成、检查通过、用户查看页面都不等于授权。

二、七个环节细分（含必读文件与关键命令）

以下每个环节列出：职责技能、触发条件、执行动作、决策点、产出、必要读取的文件与关键命令。

环节 0｜需求输入

触发：用户以任意形态提出业务需求 —— 自然语言描述 / 参考图（截图、草图，仅风格参考）/ Figma 设计稿（仅视觉组件参考，不代表需求已确认）。
  • 图中缺失的业务逻辑、状态、数据须由对话补全；流程、状态、数据来源与边界必须在简报中确认。
  • 此环节无固定必读文件；三种形态最终都汇入「环节 2 需求确认」。

环节 1｜任务启动（启动清单 · wego-github-delivery）

所有新任务（业务原型、设计系统维护、工作流维护）开工前必须按 .codex/skills/wego-github-delivery/references/task-intake.md 启动清单执行，目的是防止重复建分支、跳过需求确认和环境残留。

  1. 判断会话上下文：有活跃上下文（任务 worktree + 未冻结迭代/活跃分支）→ 走轻量启动；无上下文 → 走完整启动。
  2. 分支巡检：git branch -vv + npm run branches:stale 收口已合并 / gone 分支，闭合「PR 合并后本地分支残留」缺口。
  3. 环境同步（完整启动）：主 worktree git pull --rebase origin main；会话前置读经验摘要；处理 needs-sync 标签 PR；清理失效预览服务记录。
  4. 交付单元核对：node scripts/resolve-delivery-unit.mjs --scene {场景}，结果只能是 matched / new / conflict。
  5. 需求规格确认：matched+范围未变跳过；matched+范围变化或 new → 进入 wego-product。
  6. 工作环境就绪：new → git worktree add ../<owner>-<task> -b <分支> 独立 worktree；matched → 切换到已有 worktree。
决策点：交付单元核对结果 —— matched 接手结果指定的分支/worktree/PR；new 确认无匹配才创建新迭代与分支；conflict 停止并说明阻塞原因，不得自行选择候选。返回 new 后必须用 git branch -vv 扫一遍悬空分支，能恢复 worktree 就不新建。

环节 2｜需求确认（wego-product）

负责确认目标、范围、入口、关键路径、原型边界、状态和数据；不决定正式组件、Token、CSS 或设计系统实现。需求阶段唯一产出是需求规格说明（spec.md），按简报模板填写后经 submit-brief 自动解析校验。

  1. 创建迭代：iteration-record.mjs init，迭代 ID 形如 shop001 / bcg003-2，分类代码 shop（相册云）/ bcg（生意云）/ customer（客户云）/ infras（基础）。
  2. 写 spec.md：按简报模板填 goal / included / excluded / entry_points / critical_paths / prototype_boundaries / states / data_contract / assumptions / open_questions。
  3. 提交简报：submit-brief 解析 MD、运行充分性守门、算范围哈希 → 状态 in-development（简报开放开发，可随时改 spec 后重新 submit）。
  4. 简报开放开发：用户浏览、修改 spec、重新 submit、完成修改都不触发状态推进。
充分性守门（缺失即被拒）：目标/纳入范围/入口/关键路径/原型边界/状态必须非空；data_contract 必须非空对象；open_questions 必须为空；states 覆盖加载态、失败态、空状态（含数据产生入口引导）；数据必须有产生入口且禁止静态种子降级；关键路径首尾闭环。

环节 3｜页面设计与实现（wego-design）

基于已确认原型简报消费设计系统，在一次任务中完成可交互 App 场景。已确认简报即设计授权，范围内自主完成信息分组、布局、组件、Token、反馈和 overlay。

  1. 读输入：有效迭代 spec.md（唯一需求源）+ 设计原则 + 设计方法 + 资产地图 + 原型数据库说明。
  2. 短设计链路：理解进入页面原因 → 确定唯一首要任务/核心对象/必要状态 → 语义区域顺序 → 首屏/滚动/固定/overlay → 精确匹配页面范式（未命中用 composed）→ 组件映射（核对 usageHints / doNotInvent 后复制 Preview 变体完整 DOM）。
  3. 实现：只输出场景目录中 route.json / scene.js / scene.css；路由变化运行 build-routes.mjs 生成 wego-app/js/routes.js（生成物，禁止直接编辑）。
  4. 场景契约预检：validate-scene-contract.mjs <场景路径> 通过后再推送 PR，问题不留到合并阶段全量门禁才发现。
  5. 自动推送：完成一轮验证后由 wego-github-delivery 自动推送远端分支并创建/更新同一 PR；每次推送后必须返回在线预览链接（不只本地链接），等待 publish 部署完成（curl 校验 .wego-deployment-sha 或 gh pr checks）。
状态标注：每轮结果标明「当前状态：本地迭代中（已推送，PR #编号）」或「本地迭代中（未推送）」。
数据来源约束：场景中的商品、素材图片、头像、发布者、好友和运营文案必须优先取自 window.WEGO_PROTOTYPE_DB，不在 scene.js 临时编造或硬编码。

环节 4｜交付与 PR（wego-github-delivery）

统一管理分支、worktree、预览和 PR。一个交付单元固定一个工作分支和 worktree，同一需求固定复用同一个 PR，最多一个开放 PR。

  1. 本地迭代中（自动推进，默认）：修改 → 轻量源码检查 / 关键交互检查 → checkpoint commit → 自动推送创建/更新 PR。
  2. 预览服务：从任务 worktree 根目录启动，仅绑定 127.0.0.1；端口/PID/worktree/分支/阶段/PR 编号记录在 .tasks/preview-servers/（不得提交）。
  3. 双链接交付：业务原型在本地迭代和合并阶段都返回「本地 HTTP 预览 + 在线 PR 预览」两个链接；在线链接必须等部署完成（curl 校验部署 SHA）后才返回。
  4. 合并授权门禁：推送与创建 PR 不需要用户授权；合并进 main 必须用户明确验收通过。
决策点（合并授权）：只有用户明确表达「验收通过」「确认合格」「可以合并」才允许合并；「改好了 / 继续 / 再调整一下」不构成合并授权，必须保持 PR 开放继续本地推进。

环节 5｜验收收口（wego-design + wego-github-delivery）

用户明确表达「验收完成 / 确认合格 / 可以合并」后进入收口流程，一次性完成固化、验证与合并准备。

  1. 输出 5 维度一致性校验清单，逐项对比 spec.md 与实际实现：范围 / 入口 / 关键路径 / 状态 / 数据契约。
  2. 用户逐项确认后连续执行：confirm-brief（简报确认 → prototyping）+ submit-prototype --user-confirmed-prototype {id}（场景验证 + 固化指纹 + 确认 + 冻结，一步到 frozen）。
  3. 完整静态验证：validate-wego-design.mjs --scope=full --strict + build-routes.mjs --check + sync-wego-app-lib.mjs --check，任一失败先修复再推送。
  4. 经验收口：扫描 .tasks/experience-inbox.json，有草稿交 wego-uxsystem-iterate 四层分流沉淀，无草稿明示「本轮无经验信号」后清空；未完成本步不得进入 worktree 清理。
  5. 合并前：同步最新 main、解决冲突、复验，通过后合并 PR 进 main。
状态标注：每轮结果标明「当前状态：已验收，合并中（PR #编号）」。

环节 6｜合并与收尾清理（wego-github-delivery）

PR 合并是异步事件（网页端合并 / CI 自动合并 / 工作流维护短周期 PR 自动合并），无论谁触发，本地收口都必须完成；不在场则由后续任务启动时的分支巡检兜底补齐。

  1. 停止本地预览服务并删除服务记录（.tasks/preview-servers/）。
  2. 删除远端分支：PR 合并时自动删除；手动关闭/废弃时 git push origin --delete <branch>。
  3. 删除本地 worktree：git worktree remove <path>。
  4. 主 worktree 同步最新 main：git pull --rebase origin main。
工作流维护例外：wego-uxsystem-iterate 执行的 AGENTS.md / SKILL.md / references / experience 等权威源维护免业务验收和提交授权，验证通过后直接走短周期 PR 自动合并 main，并立即完成完整收口清理；组件/Token/Preview/UI Kit 变更不适用此例外。

关键命令

npm run worktrees:stale / worktrees:prune   # 孤儿 worktree 巡检与清理
npm run branches:prune / branches:prune-gone # merged / gone 分支收口
git worktree remove <path>  &&  git pull --rebase origin main

环节 7｜经验沉淀（wego-uxsystem-iterate）

经验沉淀由信号驱动自动执行，不等待用户触发。业务技能（product / design / delivery）在现场只识别信号、写 .tasks/experience-inbox.json 草稿（L0），不直接改经验权威源。

  • 触发信号：用户纠正、用户表达偏好（「以后都」「不要再」）、返工（同一问题第二次出现 / 验收打回重做）、踩坑（CI 失败 / 守卫拦截 / 验收打回）。
  • 收口扫描时机：wego-design 5 维度验收清单之后、合并之前，且必须在 worktree 清理之前完成（红线）。
  • 四层分流：一次性未成规律 → L1 事实 + L2 一句话摘要；同场景 ×2 或流程固定 → 毕业 L3 场景技能；已有对应场景技能 → 迭代该技能；跨场景硬约束 → 升格 L4 正式规则。

三、迭代状态机

draft→ submit-brief→ in-development（简报开放开发）→ confirm-brief（验收完成+5维校验）→ prototyping→ submit-prototype（用户明确验收通过，一步冻结）→ frozen
暂停 / 终止状态为 blocked | cancelled | superseded。冻结由脚本生成 freeze.json 快照并禁止覆盖，冻结后的记录是历史快照，不再为场景修改提供有效迭代绑定。

用户反馈分流

当前状态反馈类型处理方式
in-development已确认范围内视觉/布局/组件/Token/路由/交互调整直接修改 spec 并重新 submit-brief，不 invalidate
prototyping已确认范围内调整直接继续修改，不 invalidate
frozen已确认范围内调整先 invalidate --stage=prototype 回 prototyping（自动删 freeze.json），累计完成后用户再次明确验收通过才重新 submit-prototype
任意阶段改变目标/范围/入口/关键路径/状态/数据/可见结果先 invalidate --stage=brief，更新 spec 并重新提交确认
Agent 不得因为实现完成、检查通过、用户查看了本地页面，或自己判断「可以交付」而执行 submit-prototype；确认、测试、验收、交付、提交、部署或时间经过都不能单独推断冻结意图，冻结必须与验收收口连续执行。

六、经验体系（四层单向流动）

L0 草稿 .tasks/experience-inbox.json→ L1 事实 evidence.json→ L2 摘要 EXPERIENCE.md→ L3 场景技能 wego-scene-*→ L4 正式规则 AGENTS.md / 守卫
  • 只增不减：L1 事实不因升级或过时而删除，体量过大按年归档到 evidence-archive/。
  • 沉淀标准：可复用、可行动、非冗余；单场景特例、普通代码错误、需求临时变化、单次视觉微调不进入经验数据。
  • 沉淀即告知：🧠已沉淀经验：<简短描述>，不新增任何用户确认门禁；零信号零动作。
  • 场景技能三重挂载：description 写触发词 + 技能路由 README 登记 + 对应主技能 SKILL.md 硬挂载，三者齐全才能被触发。
  • 毕业标准：同场景 ×2 或流程固定才允许创建 wego-scene-*；不预防性建技能，达不到只留 L2。

七、高频踩坑提示（源自 EXPERIENCE.md 经验摘要）

环节教训
简报spec 多轮更新后、提交前必须全文搜索关键词统一旧描述，保证前后一致；每个入口写清触发方式、对象、按钮层级与后续行为，不明点入 open_questions 不猜测。
设计稿Figma 还原前必须确认设计稿内容，无法访问就请用户描述或给切图，禁止凭组件名猜样式；modal fullscreen 改居中弹窗须场景级恢复蒙层、提 z-index、改淡入与居中。
实现切图要偏移且不裁剪用 img 标签定位（不用 CSS 背景图，会被裁剪）；img 路径相对 index.html；新接入本地存储先 grep 现有 wego.* key，新 key 按 wego.{domain}.{entity} 命名，不迁移旧 key。
交付每次推送 PR 必须等 publish 通过并 curl 校验部署产物后返回在线链接，不得只给本地链接；PR 合并后必须清理本地分支/worktree/预览记录。
CI改 design/runtime 必须同步 lib 副本（sync-wego-app-lib --check 只读，默认写入）；Pages 预览标红多为部署延迟，先比对 .wego-deployment-sha 再排查构建。
结构业务场景功能不得放入技能目录/设计系统权威源，全局业务运行时直接放 wego-app/js 与 wego-app/css（runtime.business_file 守卫拦截）。
本梳理基于当前仓库权威文件（AGENTS.md、.codex/skills/README.md、各技能 SKILL.md 与 references、experience/EXPERIENCE.md），如工作流后续调整请以权威源为准。
