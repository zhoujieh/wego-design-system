# wego-sdd-spec 技能方向：交互规格密度足够细的 spec 生成

> 主题：AI SDD 流程里"把需求写成 spec"的独立技能。产出的 spec 同时服务两个消费者——**开发 AI**（按迭代范围+交互原型写 kuikly 代码）与**迭代画布**（spec 的可视化投影）。核心要求：**交互规格密度要足够细**，每个状态/分支/校验/边界都显式写清楚。
> 状态：方向讨论中（本次先定初版产出结构，后续随迭代画布与开发反馈不断迭代完善）。
> 创建：2026-09-04

---

## 一、定位

- **技能形态（定性 2026-09-04）**：**独立的、按需触发的技能**——不耦合进现有三技能主链路（wego-product/wego-design/wego-uxsystem-iterate），不自动接入工作流；当需要产出"细交互规格"（给开发 AI / 迭代画布消费）时**按需触发**。
- **上游输入**：用户需求描述 / 需求文档 / 参考图 / Figma 设计稿。
- **下游消费者**：①开发 AI（按 spec 写 kuikly 代码）；②迭代画布（解析 spec 生成可视化投影）；③验收（验收场景可验证）。
- **与迭代简报（wego-product）的关系**：简报是立项/范围的轻量产物（goal/范围/入口/关键路径/状态/数据契约）；本技能产出的是**更细的交互规格**（FR + 边界 + 验收场景 + 业务规则）——**在简报已确认的事实基础上细化，不重新发明业务事实**。
- **业务事实红线**：spec 内容只来自用户需求与明确确认，不从参考图/Figma/同类页面补造业务事实。

## 二、产出结构（结合两份范本重定义）

> 范本 A：`docs/sdd-spec参考/帮卖弹窗spec.md`；范本 B：`docs/sdd-spec参考/shop243 鸿蒙 1.3 — 分享面板扩展 + 灰度升级弹窗.md`。
> 两者共同骨架即本技能的产出结构，共 11 节：

| # | 节 | 内容 | 密度要求 |
| --- | --- | --- | --- |
| 1 | 元信息 | 功能分支 / 创建日期 / 状态 / 输入来源 / 关联需求文档 / Figma 设计稿(fileId) | 可追溯 |
| 2 | 画板→验收场景映射表 | Figma nodeId ↔ 状态/验收场景 | 每个状态可定位画板 |
| 3 | 用户场景与测试 | 用户故事 US（优先级）+ 验收场景（给定/当/那么） | 每个功能点有独立测试 |
| 4 | 功能需求 FR | 编号 + 描述 + **B1 7 项边界**（加载中/加载失败/空数据/边界值/权限/并发/异步时序） | 每条 FR 7 项边界逐条写 |
| 5 | 业务规则 BR | 分支逻辑 / 状态流转 / 参数路由，用枚举表（如面板标题表/平台跳转表/异常提示表/状态流转图） | 完整枚举、可验证 |
| 6 | 数据来源 | 接口/数据源表 + 字段业务含义 + 单位表（如有） | 字段单位锁定、不猜 |
| 7 | 关键实体 | 实体名 + 定义 + 状态/属性 | 名词统一 |
| 8 | 成功标准 SC | 可度量结果（准确率/时间/覆盖） | 可验收 |
| 9 | 假设 | 低风险可逆、已写明影响 | 不承载关键事实 |
| 10 | 澄清记录 Clarifications | 按 Session 分组 Q→A，结论**必须写回对应业务字段** | 不留悬案 |
| 11 | Writer 自检清单 | 可验证性/分支全覆盖/异常显式化/无技术越界/优先级/数据语义/契约对齐 | 定稿前逐项打勾 |

## 三、"交互规格密度足够细"的定义（核心）

spec 不算"够细"直到满足以下全部：

1. **状态全覆盖**：每个功能点的默认主态/输入态/完成态/异常态（加载中/加载失败/空数据/边界值/权限）都显式列出，注明「进入条件 → 可感知结果」。
2. **分支全覆盖**：所有参数取值/状态分支都有处理方式（含兜底），无遗漏——参考 BR-04 异常提示全枚举表、BR-06 面板标题判定表。
3. **校验与单位锁定**：范围校验（如 1%-300%）、精度、单位（金额/比例/小数 vs 整数）在 spec 锁定，实现/测试一律遵守——参考帮卖 spec「价格/加价字段单位表」。
4. **状态流转显式**：跨页面/跨会话状态流转用表或流程写清——参考 shop243 BR-02（授权 30 分钟流转）、FR-10（灰度弹窗分型）。
5. **子流程明确定义**：每个浮层/弹窗/面板写清「触发入口 → 来源页面 → 展示形态（蒙层+弹窗）→ 完成/取消去向」，嵌套子流程（如二级面板）单独定义（见 03 §2.3）。
6. **验收场景可验证**：每条验收场景用「给定/当/那么」写成可直接转测试断言。

## 四、澄清闭环（内置，spec 写作最难环节）

参考 shop243 范本的 clarify 流程：

```
原型/需求 → 自查补漏（≤5 问）→ 各方独立评审（产品/设计/开发）
  → 依据错误点清单生成 spec v2 → 确认"错误已修正" → 定稿
```

- 澄清结论必须**写回对应业务字段**，不能只留在 Clarifications 里。
- 影响目标/范围/入口/关键路径/状态/数据含义 → 必须询问用户；低风险可逆 → 假设；局部 → 确认后转假设/excluded。

## 五、守门与校验（供迭代画布消费）

- 结构校验：11 节齐全。
- 状态完整性：B1 边界 + 验收场景全覆盖；缺失 → 迭代画布以占位卡呈现 + 汇总缺口清单。
- 可消费性：spec 中每个状态可解析出"归属页面/顺序/主/子流程"（配合 03 §8.3 的 states 轻度增强）。
- 契约对齐：多端/前后端协作字段标注"待澄清"，契约在 plan/contracts 阶段锁定。

## 六、与迭代画布/开发 AI 的协作关系

```
用户需求/参考/Figma
  → wego-sdd-spec（产出细 spec，11 节 + 澄清闭环）
      ├─ 开发 AI：按 spec + 交互原型写 kuikly 代码
      └─ 迭代画布：解析 spec 生成可视化投影（占位卡兜底缺口）
```

- spec 先全、画布后生；两者解耦，spec 是唯一事实来源。
- 本技能与迭代画布技能均为独立技能，后续再看接入工作流。

## 七、后续迭代完善机制

- 本技能产出结构为**初版**，后续通过两类反馈持续打磨：
  1. 迭代画布消费 spec 时的缺口/解析失败 → 反哺 spec 结构；
  2. 开发 AI 用 spec 写代码时的疑问/返工 → 反哺密度标准。
- 更新产出结构 = 更新本文档 + 同步范本对照表，技能化后同步 SKILL.md。
