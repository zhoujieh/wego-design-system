# 03 · 通用技能实现方向

> 目标：把"迭代画布"从实验场景沉淀为**通用技能**——某个迭代收尾时，自动读取该迭代的资料，生成对应的迭代画布（按迭代归档、在线预览、作为开发 AI 的设计规格输入）。
> 本文是**实现方向的讨论稿**，非最终实现；关键决策点标 ❓ 待确认。

---

## 一、技能定位与输入输出

```
输入：迭代目录 _iterations/<id>/（spec / iteration.json）
      + 该迭代涉及的业务场景（wego-app/scenes/...）
      ──▶ 迭代画布生成技能 ──▶
输出：迭代画布（HTML 场景，routeId 与迭代绑定）
      权威源归档在迭代目录；在线预览可访问
      作为开发 AI 的设计规格输入
```

**技能职责**：把"迭代资料"翻译成"画布数据模型"，再走已验证的渲染管线出图。

---

## 二、数据模型：spec → 画布

核心是把迭代 spec 映射为画布的流程链/状态链/子流程。当前实验用 `SAMPLE_ITERATION` 内置样例，技能要改为**从迭代资料解析生成**。

### 2.0 输入契约：spec 必须"很全"（状态链完全由 spec 驱动的前提）

> 拍板结论：**状态链完全由 spec 驱动** → 反向要求 spec 足够全。
> **spec 范本库**（两份仓库真实 spec，均无需新增显式 states 字段）：
> - `docs/sdd-spec参考/帮卖弹窗spec.md`：状态藏在「验收场景（给定/当/那么）+ FR 边界 7 类 + 业务规则表」
> - `shop243 鸿蒙 1.3 — 分享面板扩展 + 灰度升级弹窗.md`（用户提供）：每个 FR 有**显式 B1 7 项边界**（加载中/加载失败/空数据/边界值/权限/并发/异步时序）、BR-02 **显式状态流转**、BR-04 **异常提示全枚举表**、US1 列**入口页面清单**（查看态 5 页 + 操作态 3 页）、每个 US 带 **Figma nodeId→画板映射**

**关键认识**：spec 不需要新增显式 `states` 枚举，状态本来就完整存在于 spec 的已有结构中——画布作为**消费者**解析即可：

| spec 已有结构 | 画布从中提取 |
| --- | --- |
| 用户故事/验收场景（给定/当/那么） | 主流程 + 每个功能点的状态链（默认态/输入态/完成态） |
| B1 7 项边界（加载中/加载失败/空数据/边界值/权限/并发/异步时序） | 异常态/边界态状态块（spec 声明了就要展示，不能缺失） |
| BR 显式状态流转（如 BR-02 未授权→已授权→过期） | 跨页面的状态链 |
| BR 全枚举表（如 BR-04 异常提示表 / BR-06 面板标题 / BR-08 平台跳转） | 分支判定、toast/弹窗类子状态 |
| Figma nodeId→画板映射 | 画板与状态的对应关系（画布呈现顺序） |
| 二级面板/弹窗/下载/系统交互（US4 小程序链接二级面板、US5 灰度弹窗等） | 子流程定义（触发入口/来源页面/展示形态/去向） |

**画布与 spec 的关系**：`spec 是唯一事实来源，画布是 spec 的可视化投影`。spec 缺什么，画布就缺什么（并明确提示缺什么），画布不自行补事实。

### 2.1 建议数据模型（对齐现有渲染）

```jsonc
{
  "identity": { "iteration_id", "title", "primary_scene", "related_scenes", "date" },
  "status": "prototyping | in-development | frozen",
  "goal": "迭代目标",
  "entry_points": ["入口1", "入口2"],          // ← spec.entry_points
  "included": [], "excluded": [],              // ← spec.included / excluded（范围卡片）
  "flows": [                                    // ← spec.critical_paths 为主干
    {
      "id", "title", "priority": "P1",
      "desc": "流程一句话",
      "nodes": [                                 // 主流程：一个功能点一条生命周期状态链
        {
          "label": "页面名", "routeId": "scene-route-id",
          "tab": "dongtai | null",               // host-tab 页面需补底部导航
          "states": [                             // ← spec.states 完整映射（不删减）
            { "name": "空状态", "sub": "empty-form",
              "prepare": [ { "action": "fill", "selector": "...", "value": "..." } ] }
          ]
        }
      ]
    }
  ],
  "subflows": [                                 // ← 子流程单独排版（spec 明确定义）
    {
      "title": "发布并开启帮卖",
      "nodes": [
        { "label": "发布页+帮卖弹窗", "routeId": "publish-product",
          "overlay": { "type": "resale", "sampleKey": "..." } }   // 弹窗层叠
      ]
    }
  ]
}
```

### 2.2 状态链映射规则（完全由 spec 驱动）

- **权威源**：spec 定义的完整状态集。画布**直接消费 spec 声明的状态**，不自行发明、不自行删减。
- **状态不能缺失**：spec 定义的状态，画布必须全部展示；spec 有但当前场景未实现 UI 的状态，用**占位卡**呈现，**不因场景没实现而隐藏**。
- **占位卡（已确认 2026-09-04）**：一张"规格占位卡"承载 spec 声明但场景未实现的 UI 状态——卡片上标明 spec 声明的状态名/引用（如"B1 加载中 · FR-06"）、标记"待业务场景补充 UI"，不伪造内容。**同时兼作缺口排查清单**：所有占位卡汇总即"本迭代还需补充哪些 UI"，用户排查缺口一目了然。
- **过滤例外**：仅当 spec 明确不纳入（如已移除的需求、明确不要的过渡态）才不展示。
- **排序**：按 spec 声明的业务生命周期（或验收场景顺序）从左到右。

### 2.3 子流程（由 spec 定义 · 按"定义→摆放→数据来源"展开）

**① 定义（是什么）**：附着在宿主页面之上、由页内入口触发、以"蒙层+浮层"形态呈现、结束后返回宿主或跳转的**交互单元**（帮卖弹窗、分享面板、小程序二级面板、灰度升级弹窗、下载进度、toast 等）。与主流程的区别：主流程=页面级导航（页面A→B），子流程=页面内浮层交互（页面A 上弹浮层）。子流程可**嵌套**（分享面板→小程序二级面板）。spec 需为每个子流程写清「触发入口 → 来源页面 → 展示形态 → 完成/取消去向」。

**② 摆放（画布上怎么放）**：实验已验证——子流程单独排版成一条链，每个节点 = "来源页面（蒙层下）+ 弹窗（蒙层上）"真实层叠，复用真实弹窗运行时；嵌套子流程（二级面板）也按真实层叠摆。子流程链放在主流程对应节点的旁/下方，标签标明触发入口；来源页面无需可操作（浮层定位基准）。

**③ 数据来源**：子流程的 UI/交互来自**场景内已实现的真实运行时**（画布复用，不重写）；展示的具体样例数据（如弹窗内商品）来自**场景内已定义的样例集**（如帮卖弹窗 RESALE_SAMPLES 内置 first-resale-free-single）；spec 只定义子流程的交互结构（入口/形态/去向/状态链），**不定义 UI 数据细节**。场景未实现该子流程 → 占位卡（§2.2）。

## 三、渲染管线（复用已验证机制）

```
解析迭代资料 → 构建数据模型
  → renderStatic（迭代信息/范围/入口卡片）
  → 逐流程渲染 flowMarkup（节点=状态块横排 + 连线）
  → 逐状态块 renderSceneTo(routeId, host) 实时渲染真实场景
  → 按标记：mountBottomTab（host-tab 补底部导航）
  → 按标记：mountOverlay（伪造 ctx 平铺弹窗层叠）
  → runPrepare（fill/click/scrollTo 驱动到目标状态）
  → createCanvas（无限画布：平移/缩放/适配/resize 拖高）
```

所有机制已在实验验证，技能化时**把这些代码从"画布场景"抽象为可复用生成器**。

## 四、归档与在线预览（权威源 + 快照）

**问题背景**：之前已确认 "Pages 构建禁止发布 `_iterations/` 目录"，但画布要求"权威源在迭代 + 在线预览"。

**化解方向**（实验场景的落地方式，技能化沿用）：

- **权威源**：迭代画布的数据/生成配置存放在迭代目录 `_iterations/<id>/`（与迭代资料同源）。
- **生成快照**：迭代收尾时，由生成器产出可发布的画布快照到**可发布目录**（如 `wego-app/scenes/infras/迭代画布/<iteration-id>/` 或专门的画布归档区），该目录参与 Pages 发布。
- **预览**：快照随场景路由在线访问；权威源改动需重新生成快照（生成器是"权威源 → 快照"的唯一通道）。

❓ 待确认：快照目录的规范位置、快照与权威源的版本对应、是否支持"权威源改动后一键重新生成"。

## 五、通用技能的落点与边界

### 5.1 技能形态与触发时机

- **独立技能**（已拍板）：沉淀为独立场景技能（如 `wego-scene-iteration-canvas`），**先独立存在，后续再看如何接入工作流**。
- **触发时机**：迭代收尾时（终局确认/验收前后）半自动调用，生成该迭代的迭代画布。

### 5.2 与现有工作流的关系

- 画布本身是一个场景（已用走查工具入口接入），技能 = 场景内容的生成器。
- 不改变既有迭代/验收流程，只在收尾环节增加"生成迭代画布"这一交付物。

### 5.3 边界（明确不做）

- 不做画布内直接编辑业务场景（画布是投影，改动走业务场景本身）。
- 不发明 spec 没有的状态（spec 有而场景未实现的，用占位卡呈现；spec 没有的不展示）。
- 不替代 `prototype_brief` / spec（画布消费它们，不生产它们）。
- spec 需要由上游（产品/设计）写全，技能不负责补全 spec 内容。

## 六、验收标准（技能化后）

- [ ] 给定一个真实迭代目录，能自动生成对应迭代画布（入口/流程/状态链/范围与 spec 一致）。
- [ ] 画布中所有页面为真实场景 DOM 投影，业务场景改动后重新生成即同步。
- [ ] 弹窗子流程呈现真实层叠（蒙层下页面 + 蒙层上弹窗）。
- [ ] host-tab 页面底部导航补全。
- [ ] 无限画布（缩放 6%~1000%、平移、适配、高度拖拽）。
- [ ] 按迭代归档 + 在线预览可访问。
- [ ] 缺 spec 数据时给出明确占位与说明，不编默认值。
- [ ] spec 声明但场景未实现 UI 的状态 → 占位卡呈现（标 spec 引用 + "待业务场景补充 UI"），占位卡可汇总为缺口排查清单。

3. **独立技能** → 先做独立场景技能，后续再看如何接入工作流。

**范本确认（2026-09-04 补充）**：两份 spec 范本（帮卖 + shop243）均无显式 states 枚举，状态完整存在于"验收场景 + B1 7 项边界 + BR 状态流转/枚举表 + Figma 画板映射"中 → 画布以消费者身份解析 spec 已有结构，**不需要逼 spec 新增 states 字段**（见 §2.0）。

### 7.2 待讨论（❓）

1. ~~spec 的"状态完整性"如何校验~~ → **已确认**：占位卡方案兜底——spec 声明但场景未实现 → 占位卡呈现 + 汇总为缺口清单；从源头仍建议 spec Writer 自检清单加"B1 边界 + 验收场景全覆盖"检查。
2. ~~子流程的数据从哪来~~ → **已给出方向**（见 §2.3 ③）：子流程 UI/交互取场景内真实运行时，样例数据取场景内样例集，spec 只定义交互结构；场景未实现 → 占位卡。待后续实现验证。
3. **快照目录规范与"一键重新生成"（待讨论）**——背景：GitHub Pages 禁止发布 `_iterations/` 目录 → 迭代画布的**权威源（spec/场景/编排）**存迭代目录（不可发布），**生成的画布 HTML 快照**须落到可发布目录（GitHub Pages 可访问，如 `previews/`）才能在线预览。"一键重新生成" = 迭代内容更新后跑一次生成器刷新快照，不手工维护两份。**待定**：快照目录放哪、命名与版本对应、生成器形态（命令行/脚本/CI）。
4. **同一页面多视口（待讨论）**——背景：一个状态块固定 393×852 视口只能显示页面某一段；"多视口"= 同一页面同一业务状态的不同滚动位置（顶部导航区 / 中部内容 / 底部 tab 栏）分别平铺，让开发 AI 看全页面。**与"多状态块"区别**：多状态块 = 不同业务状态（空/填/完成）；多视口 = 同一状态不同滚动位置。**待定**：用多状态块扩展（滚动位置也做块）还是新增"视口配置"机制。
5. **prepare 状态脚本（待讨论）**——背景：画布状态块要展示"填完整表单"等状态，需先对真实 DOM 执行操作（fill 填字段 / click 点击 / scrollTo 滚动）才能到达；prepare = 这些"到达目标状态的操作指令"。当前实验硬编码在 SAMPLE_ITERATION。**待定**：指令存哪——spec（偏重）/ 迭代资料 iteration.json / 画布作者生成时补充。

## 八、spec 上游调研：格式评估与生成技能（2026-09-04）

> 背景：迭代画布是 spec 的"可视化投影"（消费者），上游 spec 的完整度直接决定画布质量。用户提出两个问题：①当前 spec 生成格式是否需要调整？②生成 spec 没有专门技能，是否值得沉淀？

### 8.1 当前 spec 生成现状（已核实）

- **唯一 spec 形态 = 迭代"需求规格说明"**，由 `wego-product` 技能产出，按 `brief-template.md` 填写，`submit-brief`（薄档）/ `confirm-brief`（终版全量）脚本守门。
- 字段：goal / included / excluded / entry_points / critical_paths / prototype_boundaries / states / data_contract / assumptions / open_questions / Clarifications。
- **无独立 spec 生成技能**；详细功能 spec（帮卖、shop243 范本：FR + B1 边界 + 验收场景 + Figma 映射）在本仓库是零散产出，无技能承载。

### 8.2 当前 spec 对画布的友好度评估（对照 §2.0 解析需求）

| 画布需要（§2.0） | 当前 wego spec 现状 | 差距 |
| --- | --- | --- |
| 入口 | entry_points ✅（位置/可见条件/触发） | 无 routeId/页面归属，需结合路由映射 |
| 主流程 | critical_paths ✅（起点→操作→中间态→结果，[P1]） | 可直接消费，无需调整 |
| 状态链 | states ✅（进入条件→可感知结果）但**全局扁平列表** | **最大差距**：不归属页面/流程、无展示顺序、主/子流程混排 |
| 子流程 | ❌ 无显式定义（如 resale-popup-open 只是 states 一条） | 缺"触发入口/来源页面/展示形态/去向" |
| 验收场景 | ❌ 无（只有 visible_result） | 缺"给定/当/那么"可验证对应 |
| Figma 画板映射 | ❌ 无 | 详细 spec（帮卖/shop243）才有 |

### 8.3 格式调整建议：轻度增强，不大改模板

**理由**：current spec 是"简报→页面"轻量风格且已有守门/流程稳定；详细 spec 范本（FR/B1/验收场景）是给开发 AI 的更重规格。**不建议把两档合并**，也不建议给简报模板加 FR 编号/B1 七项。

**建议的轻度增强（brief-template 可选字段）**：
1. `states` 规范补三条可选项：**归属页面/流程**（挂到哪个节点）、**生命周期顺序**（同页展示顺序）、**主/子流程标记**（是否弹窗/浮层子流程）。
2. 子流程用规范写法：`来源页面 → 触发入口 → 展示形态（蒙层+弹窗） → 完成/取消去向`。
3. 不新增 states 枚举字段（§7.1 范本确认）。

**兜底分工**：spec 不足的部分（状态归属、顺序、子流程形态、Figma 映射）由**迭代画布生成时的编排层补充**（实验已证明 SAMPLE_ITERATION 可手工编排），spec 保证"状态齐全不缺失"，编排层保证"画布呈现正确"。

### 8.4 是否沉淀独立 spec 生成技能——建议沉淀

**现状缺口**：详细 spec 无技能承载，质量依赖临场发挥；且迭代画布是 spec 消费者，spec 质量直接影响画布与开发 AI 交付。

**建议沉淀一个独立 spec 技能**（如 `wego-spec`）：
- **上游**：消费用户需求/参考/Figma → 产出标准 spec（含画布可消费结构：入口/流程/状态链/子流程/验收场景）。
- **内置澄清流程**：参考 shop243 范本的 clarify 闭环（Q→A→写回字段→各方评审→定稿），这是 spec 写作最难也最关键的环节。
- **守门**：借鉴 speckit 思路——结构校验 + 状态完整性（B1 边界/验收场景全覆盖）+ 占位卡缺口清单。
