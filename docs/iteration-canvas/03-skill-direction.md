# 03 · 通用技能实现方向

> 目标：把"迭代画布"从实验场景沉淀为**通用技能**——某个迭代收尾时，自动读取该迭代的资料，生成对应的迭代画布（按迭代归档、在线预览、作为开发 AI 的设计规格输入）。
> 本文是**实现方向的讨论稿**，非最终实现；关键决策点标 ❓ 待确认。

---

## 一、技能定位与输入输出

```
输入：迭代目录 _iterations/<id>/（spec / iteration.json）
      + 该迭代涉及的业务场景（wego-app/scenes/...）
      ──▶ 迭代画布生成技能 ──▶
输出：迭代画布（HTML 场景，routeId 与迭代绑定）
      权威源归档在迭代目录；在线预览可访问
      作为开发 AI 的设计规格输入
```

**技能职责**：把"迭代资料"翻译成"画布数据模型"，再走已验证的渲染管线出图。

---

## 二、数据模型：spec → 画布

核心是把迭代 spec 映射为画布的流程链/状态链/子流程。当前实验用 `SAMPLE_ITERATION` 内置样例，技能要改为**从迭代资料解析生成**。

### 2.1 建议数据模型（对齐现有渲染）

```jsonc
{
  "identity": { "iteration_id", "title", "primary_scene", "related_scenes", "date" },
  "status": "prototyping | in-development | frozen",
  "goal": "迭代目标",
  "entry_points": ["入口1", "入口2"],          // ← spec.entry_points
  "included": [], "excluded": [],              // ← spec.included / excluded（范围卡片）
  "flows": [                                    // ← spec.critical_paths 为主干
    {
      "id", "title", "priority": "P1",
      "desc": "流程一句话",
      "nodes": [                                 // 主流程：一个功能点一条生命周期状态链
        {
          "label": "页面名", "routeId": "scene-route-id",
          "tab": "dongtai | null",               // host-tab 页面需补底部导航
          "states": [                             // ← spec.states 过滤后映射
            { "name": "空状态", "sub": "empty-form",
              "prepare": [ { "action": "fill", "selector": "...", "value": "..." } ] }
          ]
        }
      ]
    }
  ],
  "subflows": [                                 // ← 子流程单独排版
    {
      "title": "发布并开启帮卖",
      "nodes": [
        { "label": "发布页+帮卖弹窗", "routeId": "publish-product",
          "overlay": { "type": "resale", "sampleKey": "..." } }   // 弹窗层叠
      ]
    }
  ]
}
```

### 2.2 状态链映射规则（从实验沉淀）

- **权威源**：spec 的 `states` 字段。
- **过滤**：去掉故障注入态（loading / load-failed / publish-failed）与用户明确不要的过渡态。
- **保留**：功能主状态（空/填写/完整/完成）、校验、多值录入、弹窗打开。
- **排序**：按业务生命周期从左到右（空 → 填写 → 完整 → 完成）。
- **无对应 UI 的状态**：不伪造；在状态标签标注"业务场景待补充状态"（同时作为给开发 AI 的规格缺口提示）。

### 2.3 子流程判定

- 弹窗 / 半屏 / 动作面板等"浮层类"交互 → 子流程单独排版，不混进主流程。
- 展示方式：复用真实弹窗运行时（伪造 ctx），呈现"蒙层下来源页面 + 蒙层上弹窗"真实层叠。

## 三、渲染管线（复用已验证机制）

```
解析迭代资料 → 构建数据模型
  → renderStatic（迭代信息/范围/入口卡片）
  → 逐流程渲染 flowMarkup（节点=状态块横排 + 连线）
  → 逐状态块 renderSceneTo(routeId, host) 实时渲染真实场景
  → 按标记：mountBottomTab（host-tab 补底部导航）
  → 按标记：mountOverlay（伪造 ctx 平铺弹窗层叠）
  → runPrepare（fill/click/scrollTo 驱动到目标状态）
  → createCanvas（无限画布：平移/缩放/适配/resize 拖高）
```

所有机制已在实验验证，技能化时**把这些代码从"画布场景"抽象为可复用生成器**。

---

## 四、归档与在线预览（权威源 + 快照）

**问题背景**：之前已确认 "Pages 构建禁止发布 `_iterations/` 目录"，但画布要求"权威源在迭代 + 在线预览"。

**化解方向**（实验场景的落地方式，技能化沿用）：

- **权威源**：迭代画布的数据/生成配置存放在迭代目录 `_iterations/<id>/`（与迭代资料同源）。
- **生成快照**：迭代收尾时，由生成器产出可发布的画布快照到**可发布目录**（如 `wego-app/scenes/infras/迭代画布/<iteration-id>/` 或专门的画布归档区），该目录参与 Pages 发布。
- **预览**：快照随场景路由在线访问；权威源改动需重新生成快照（生成器是"权威源 → 快照"的唯一通道）。

❓ 待确认：快照目录的规范位置、快照与权威源的版本对应、是否支持"权威源改动后一键重新生成"。

## 五、通用技能的落点与边界

### 5.1 技能放哪里、何时触发

- 沉淀为仓库内技能（如 `wego-scene-iteration-canvas` 或并入 `wego-uxsystem-iterate` 的迭代收尾流程）。
- **触发时机**：迭代收尾（终局确认/验收前后）自动/半自动生成迭代画布。

### 5.2 与现有工作流的关系

- 画布本身是一个场景（已用走查工具入口接入），技能 = 场景内容的生成器。
- 不改变既有迭代/验收流程，只在收尾环节增加"生成迭代画布"这一交付物。

### 5.3 边界（明确不做）

- 不做画布内直接编辑业务场景（画布是投影，改动走业务场景本身）。
- 不自动发明 spec 没有的状态（只标注待补）。
- 不替代 `prototype_brief` / spec（画布消费它们，不生产它们）。

---

## 六、验收标准（技能化后）

- [ ] 给定一个真实迭代目录，能自动生成对应迭代画布（入口/流程/状态链/范围与 spec 一致）。
- [ ] 画布中所有页面为真实场景 DOM 投影，业务场景改动后重新生成即同步。
- [ ] 弹窗子流程呈现真实层叠（蒙层下页面 + 蒙层上弹窗）。
- [ ] host-tab 页面底部导航补全。
- [ ] 无限画布（缩放 6%~1000%、平移、适配、高度拖拽）。
- [ ] 按迭代归档 + 在线预览可访问。
- [ ] 缺 spec 数据时给出明确占位与说明，不编默认值。

---

## 七、待讨论 / 未决项（❓）

1. 状态链映射是否完全由 spec.states 驱动，还是需要画布作者人工补 prepare 指令（填值）？
2. 子流程的样例数据（如帮卖弹窗 sample）从哪来——场景内已定义，还是迭代资料需补充？
3. 快照目录规范与"一键重新生成"的交互形态。
4. 通用技能是独立 `wego-scene-*` 技能，还是并入现有迭代收尾流程？
5. 是否要支持"同一页面多视口"（如动态流同时展示滚动顶部/中部/底部）——由多状态块表达还是新增机制？
