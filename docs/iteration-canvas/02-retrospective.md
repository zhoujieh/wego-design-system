> 对"迭代画布"实验性任务的完整复盘：需求如何演变、哪些方案被否决及原因、哪些技术验证成功、踩了哪些坑、沉淀出什么结论。

## 一、需求演变时间线

| 版本 | 形态 | 用户反馈 | 走向 |
| --- | --- | --- | --- |
| **v1 卡片入口版** | 流程节点 = 卡片入口，点进去看页面 | "整体完全不符合预期，预期是页面直接平铺整个画板、以 iframe 形式平铺展示，不是一个个入口；移动端无法缩放平移" | ❌ 否决，转向 iframe 平铺 |
| **v2 iframe 平铺版** | 每个节点 = `<iframe src="#/routeId">` 平铺 + 单指拖拽双指捏合 | "iframe 嵌套的话每一个 iframe 都是能操作的，而且显示的内容也不全" | ❌ 否决，探索 Playwright 快照 |

## 二、方案对比与结论

| 维度 | 卡片入口 | iframe | 静态截图 | Playwright 快照 | **直接摆上去（真实投影）** |
| --- | --- | --- | --- | --- | --- |
| 平铺感 | ✗ 入口列表 | ✓ | ✓ | ✓ | ✓ |
| 内容完整性 | 需点开 | ✗ 固定视口裁剪 | ✓ | ✓ | ✓（配合拖高看全） |
| 交互安全 | — | ✗ 每个 iframe 可操作误触 | ✗ 无交互 | ✗ 无交互 | ✓ 浏览态锁定、点选解锁 |
| 可编辑 | ✗ | ✓ | ✗ | ✗ | ✓（真实 DOM） |
| 随场景同步 | ✗ | 需重建 | ✗ | ✗ | **✓ 实时投影** |
| 结论 | ❌ | ❌ | ❌ | ❌ | ✅ |

**关键洞察**：用户始终要的是一张"**活的、真实的、平铺的**"规格图。前四个方案分别牺牲了"平铺 / 真实 / 活"其中之一，只有"真实 DOM 投影"同时满足三者。

## 三、技术验证成功点

### 3.1 `renderSceneTo(routeId, host)`：场景渲染到指定容器

- `app.js` 暴露 `window.WegoApp.renderSceneTo`，返回 `Promise<{destroy}>`。
- 场景渲染目标由 host 决定（`sceneContext(scene, host)`），画布逐状态块调用。
- **同步验证**：改业务场景 `scene.js` 模板文本 → 画布刷新即新内容（实时投影，非快照）。

### 3.2 prepare 指令：驱动真实场景到目标状态

- 指令：`fill`（用原生 setter + input/change 事件，兼容受控输入）、`click`、`scrollTo`。
- 验证："填完整"块 13 个字段全部填满；"填写中"填基础字段。

### 3.3 弹窗平铺：伪造 ctx 复用真实弹窗运行时

- 不拷贝弹窗模板、不触发全局 overlay；用**伪造宿主 ctx**（`openSheet` 把弹窗渲染进画板容器，其余动作安全忽略）调 `openAgentResalePopup`。
- 结果：真实弹窗 DOM + 真实事件绑定，渲染在画板内，层叠正确。

### 3.4 画板定位基准：通用浮层机制

- 画板容器加 `transform: translateZ(0)`，成为内部 fixed 元素的包含块。
- 结果：`.modal / .actionsheet / .toast` 等所有浮层相对**当前画板**定位，只覆盖本画板——**一个机制解决所有浮层归属**。

### 3.5 底部导航补全

- `album-product-feed` 是 host-tab 页面，底部 `bottom-nav` 属宿主外壳（index.html 全局），不随场景模板渲染。
- 画布按 `tab` 标记把 `bottom-nav`（复用全局样式）补到画板底部，激活对应 tab。

### 3.6 无限画布

- CSS transform（`translate + scale`），单指平移、双指捏合、滚轮缩放、双击/按钮缩放；缩放放开到 6%~1000%；初始 fit 自动适配；resize 高度换算用 `canvas.getScale()`。

## 四、踩坑记录（经验教训）

### 4.1 iframe 的双硬伤（已否决方案的根因）

1. 每个 iframe 都加载完整 `app.js`，所有事件全活 → 浏览画布时误触页面。
2. iframe 固定视口（900px），长表单被裁剪（发布表单实际 1468px）。

**教训**：把"可运行的 App"嵌进画布，与"画布自己可拖拽"天然冲突，不是配置能解决的。

### 4.2 静态快照再完整也不是"活"的

Playwright 抓全 DOM 可行（333KB、全字段可见），但用户一句话否掉：**"页面不是都画好了吗？直接摆上去"**。规格图的终点是"真实 + 同步"，不是"完整截图"。

### 4.3 v3 遗留的 `modal { position: static !important }` 与新需求冲突

- v3 为了让长表单内容完整撑开（不被 852 视口裁剪），加了把 modal 改 static 的 `!important` 规则。
- v5 需要弹窗"蒙层上覆盖"的真实层叠，这条遗留规则直接导致 modal 变成 static 垂直排列。
- **教训**：演进类需求要主动清理与旧目标绑定的兼容代码；新目标（真实层叠）确定后，旧规则的 `!important` 是最大阻碍。

### 4.4 CSS 异步按需加载导致验证时序假象

- 场景 scene.css 是按需异步注入的，过早查询会得到"规则未加载"的错误结论（误判为 bug，实际是时序）。
- **教训**：验证时先确认样式表已就绪（等待加载完成信号），再做 computed style 断言。

### 4.5 状态链必须按 spec，不主观拍脑袋

- 用户对"多状态数据结构"的第一版不满意，明确要求**按 spec 规格文档**来排状态，且砍掉加载中/发布中（场景无对应 UI、发布后已表达完成）。
- **教训**：状态链的权威源是迭代 spec 的 `states`；画布不自行发明状态，场景没有的状态不伪造（标注待补）。

### 4.6 主流程 / 子流程的排版边界

- 用户要求"主流程只放当前的页面，子流程单独排版"。弹窗（帮卖设置）不再作为主流程状态混排，而是独立子流程链 + 真实层叠展示。
- **教训**：流程导航与页面展示的语义要分清——主流程讲"这条流程怎么走"，子流程讲"这个弹窗长什么样、盖在什么上面"。

## 五、沉淀结论（可复用到通用技能）

1. **范围强一致**：画布 = 迭代 spec 的可视化落点；状态链以 spec.states 为权威源。
2. **真实投影**：页面 = `renderSceneTo` 实时渲染的真实场景 DOM；业务改动自动同步。
3. **通用浮层定位**：画板 `transform` 定位基准，一个机制管所有浮层。
4. **弹窗复用运行时**：伪造 ctx 调真实弹窗 API，不拷贝模板、不改业务。
5. **host-tab 补导航**：宿主外壳级 UI（底部 tab）由画布按需补全。
6. **验证纪律**：样式按需加载要等就绪；遗留 `!important` 会与新目标冲突，及时清理。
