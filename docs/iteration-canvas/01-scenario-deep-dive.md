# 01 · 真实场景深入理解

> 本文件沉淀"迭代画布"要服务的真实业务场景。它不是一次普通的画图需求，而是微购 **AI SDD 开发流程**中的一个环节，理解这一点决定了画布的一切设计取舍。

---

## 一、业务背景：AI SDD 开发流程

微购的移动端产品（kuikly 架构）采用 **AI SDD（Spec-Driven Development）** 流程开发：

```
迭代需求（spec） + 交互原型（HTML 场景） ──输入──▶ 开发 AI ──▶ 写 kuikly 代码
```

- **输入给开发 AI 的材料**：① 本迭代的需求规格（spec）；② 交互原型（`wego-app/scenes/` 下已实现的可交互 HTML 场景）。
- **开发 AI 的职责**：严格按本迭代范围 + 参考交互原型，产出 kuikly 架构代码。

**迭代画布在这个流程中的位置**：它把"本迭代的规格 + 原型"组合成一张**一图看懂**的设计规格页，让开发 AI 能快速定位"本次迭代有哪些入口、每条流程怎么走、每个功能点的完整状态链、范围边界在哪"，从而不越界、不遗漏地写代码。

---

## 二、角色与交付对象

| 角色 | 关注点 |
| --- | --- |
| **UX 设计中心（本画布的作者）** | 把设计意图、状态细节、范围边界清晰表达给下游 |
| **开发 AI（第一交付对象）** | 按范围 + 原型写代码；需要"快速定位本次要做什么、做到什么程度" |
| **产品 / 业务（次要读者）** | 快速过目迭代全貌、验收范围 |

**核心推论**：画布的首要读者是"会写代码的 AI"，所以它必须：
1. **范围强一致**——严格对齐迭代 spec（入口/流程/状态/数据契约），不能多、不能少；
2. **可定位**——每个页面块标注 routeId、状态名、spec 状态标识，开发 AI 能顺藤摸瓜找到对应场景与代码；
3. **真实**——展示的就是线上原型真实渲染的样子，不是示意，避免"AI 看图猜实现"。

---

## 三、核心诉求拆解（按讨论演进的最终形态）

### 3.1 按迭代交付，范围强一致

- 画布属于**某个迭代**，不是独立设计工具。
- 交付时明确：**这个迭代有哪些入口、各自的流程分别是什么、范围（纳入/不纳入）是多少**。
- 画布内容与 `prototype_brief` / spec 高度一致，是"本次迭代需求的可视化落点"。

### 3.2 类 Figma 无限画布

- 页面平铺在一张无限画布上，可**放大缩小 + 平移**（单指拖拽、双指捏合、滚轮缩放）。
- 不是一个个入口卡片列表，而是**页面本身直接平铺在画板上**。

### 3.3 页面是"真实 DOM 的实时投影"，不是静态/嵌套

历经四轮否决后确定：

| 方案 | 结论 | 否决原因 |
| --- | --- | --- |
| 卡片入口节点画布 | ❌ | 用户预期是"页面直接平铺整个画板"，不是一个一个入口；移动端无法缩放平移 |
| iframe 平铺运行实例 | ❌ | 每个 iframe 可操作导致误触；固定视口导致长表单被裁剪（发布表单实际 1468px） |
| 纯静态截图 | ❌ | 不可编辑，不是用户想要的 |
| Playwright 逐页抓取 DOM 快照 | ❌ | "页面不是都画好了吗？直接摆上去，为什么还要 Playwright 一个一个看" |
| **直接摆上去（实时投影）** | ✅ | 场景渲染到画板容器 = 真实场景 DOM，活的、可交互、随业务场景改动自动同步 |

**技术机制**：`app.js` 暴露 `window.WegoApp.renderSceneTo(routeId, host)`——场景的渲染目标由调用方传入的 host 决定，画布对每个状态块调一次，把真实场景 DOM 渲染进画板容器。业务场景改任何内容，画布刷新即最新。

### 3.4 多状态：一个功能点 = 一条生命周期状态链

- 一个功能点（如"发布产品"）不是单页，而是完整生命周期：**空状态 → 填写中 → 填完整 → 发布完成**。
- 状态以**迭代 spec 的 `states` 为准**（如 `empty-form`、`field-validation`、`multi-value-entry`、`resale-popup-open`、`publish-success`），去掉故障注入态（loading/load-failed/publish-failed）与用户明确不要的过渡态。
- 每个状态由**状态脚本（prepare 指令：fill/click/scrollTo）**在真实场景 DOM 上执行，驱动到目标状态（如"填完整"把 13 个字段全部填满）。

### 3.5 子流程单独排版，弹窗真实层叠

- **主流程**只放当前功能的页面/状态；**子流程**（如帮卖设置弹窗）单独排版，不混进主流程状态链。
- 弹窗展示的是**真实弹窗实例**，且复现真实层叠：**蒙层下为来源页面（发布表单），蒙层上为弹窗**——不是弹窗单独一张图，也不是场景列表入口。

### 3.6 规格输入、默认视口与交互细节

- **默认视口**：iPhone 15 Pro（393×852）。
- **高度自调**：画板高度可拖拽（需要多高拉多高，长页面看全）。
- **缩放**：初始自动适配；放开到 6%~1000%。
- **通用浮层定位**：画板容器成为内部浮层的定位基准，弹窗/蒙层/键盘/toast 都只覆盖自己这个画板，不漂到别处。

---

## 四、边界与约束

- **不改业务场景**：画布是"投影"，不是"拷贝"；业务场景保持原样，改动由画布实时同步。
- **范围与简报强一致**：画布的状态链、流程、范围必须与迭代 spec 一致；spec 没有的状态不硬造（如加载中/发布中在场景无对应 UI 时不伪造，标注为待补）。
- **按迭代归档 + 在线预览**：画布属于迭代、随迭代归档、可在线访问。
- **本地迭代与验收**：画布本身作为场景，纳入仓库的迭代/走查流程。

---

## 五、对"通用技能化"的启示

真实场景决定了技能的核心输入输出：

- **输入**：迭代目录（`_iterations/<id>/` 的 spec/iteration.json）+ 该迭代涉及的场景库。
- **核心转换**：把 spec 的 `entry_points / critical_paths / states` 映射为画布的"流程链 + 状态链 + 子流程"数据模型。
- **渲染**：复用 `renderSceneTo` + prepare 状态脚本 + 弹窗/底部导航/画板定位机制。
- **产出**：按迭代归档的迭代画布场景，在线预览，作为开发 AI 的设计规格输入。
