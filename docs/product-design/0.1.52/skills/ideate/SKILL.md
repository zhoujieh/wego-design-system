# 创意构思

你的任务是为用户的想法生成设计概念。

遵循 [$index](../index/SKILL.md) 中的共享产品设计路由指导。

## 关键覆盖规则

- 继续之前，先参考插件路由 [$index](../index/SKILL.md)。
- 遵循 [$critical-overrides](../../references/critical-overrides.md)。

## 用户上下文

开始前，加载 [$user-context](../user-context/SKILL.md)，并在本地 shell 访问可用时运行其预检脚本。

将提供的产品 URL、Figma 文件、截图、参考图像、代码库路径、Storybook、设计令牌、设计系统、品牌资产、组件参考、浏览器偏好和分享目标附加到图像生成中，以使其与设计简报保持一致。

不要检查每个已保存的参考。只检查当前任务需要的。

## 工作流程

在 `$get-context` 满足最低要求的设计简报之前，不要生成图像。

在生成图像之前：

1. 理解简报。

- 确定目标：组件、屏幕、功能/工作流或广泛的产品创意。
- 确定目标用户、产品界面和目标。
- 保留用户的硬性约束。
- 如果最低要求的设计简报未满足，运行 `get-context`。

2. 解析上下文。

- 使用提供的文件、截图、链接和可见参考。
- 在本地工作区中，查找附近的设计文档和其他本地视觉上下文。
- 检查可能的设计上下文文件夹，如 `user-context`、`storybook/`、`.storybook/`、`design-system/`、`design-systems/`、`tokens/`、`components/`、`app/` 和生成的原型根目录。
- 在现有项目中，在生成之前查找现有产品截图、类似流程、Storybook 捕获、设计令牌和组件参考。如果现有应用无法访问，询问用户是否可以提供与其正在构建的屏幕类似的示例屏幕。确保将设计语言和设计令牌添加到图像生成提示中。

3. 直接检查参考。

- 在生成之前查看截图、图像、Figma 框架、应用界面或其他视觉参考。
- 不要仅从文件名推断。
- 如果命名的本地路径或参考不可见，停止并询问用户确认路径、上传文件、启动本地应用或指向正确的工作区。

4. 决定变化模式。

- 如果存在有用的本地设计上下文且用户未要求新风格，保持在现有方向内。
- 如果不存在有用的设计上下文，或用户要求进行广泛探索，同时变化概念和视觉系统。
- 对于特定组件或现有界面，在变化品牌风格之前，先变化结构、交互、层次和强调。
- 对于广泛的产品创意，探索三种有意义的不同产品方向。

5. 在图像生成之前选择目标尺寸。

- 选择最匹配用户请求和任何提供的视觉参考的尺寸。
- 移动应用：`390 x 844`。
- 平板应用：`834 x 1194`。
- 桌面应用、仪表板、管理后台或 SaaS：`1440 x 1024`。
- 落地页或营销页面：`1440` 宽且可滚动。
- 模态框、面板、小部件或组件：自然容器大小。
- 提供的截图、Figma 框架、模型或参考图像：当用户希望从该视觉继续时，匹配其尺寸和纵横比。
- 避免拥挤。使设计干净地适应所选尺寸，具有真实的间距、可读的类型和没有裁剪的内容。
- 在每个图像生成提示中包含所选尺寸。

6. 检查访问差距。

- 如果由于认证、权限、登录过期、缺少范围、可疑的空结果或不可用的本地状态而无法访问连接器、参考或文件，停止。
- 清楚命名差距并询问是排除故障访问还是继续不使用该来源。
- 不要在默默忽略命名参考的情况下生成图像。

7. 将用户提供的图像和模型附加到图像生成调用以及你的设计简报中。

8. 生成 3 个独立选项，它们具有不同的信息层次、布局策略、交互模型或产品框架。

你必须遵循的规则：

- 使用下面的图像生成提示。
- 使用内置的图像生成工具。
- 除非用户覆盖数量，否则准确生成三个独立图像。
- 独立启动每个图像生成调用。不要使用 `Promise.all` 批处理图像生成调用，将它们收集到有序数组中，或按请求顺序重放它们。
- 每个选项必须是其自己的图像生成结果。不要在一个图像中放入多个想法。
- 在生成之前给每个方向一个独特的描述性名称，但不要将其称为 `option 1`、`option 2` 或 `option 3`，也不要将计划的数字标签放入图像生成提示中。并行结果可能以与请求不同的顺序到达。
- 仅在图像生成结果出现在线程中后才对选项编号。唯一权威的选项顺序是这些生成图像结果在当前线程中显示的顺序。忽略计划的概念顺序、原始请求链、提示提交顺序、`Promise.all` 结果顺序、批处理顺序、数组索引、重试顺序和假设的完成顺序。
- 所有结果返回后，将每个可见的选项编号绑定到该显示顺序中的结果。不要在最终选择消息中命名或描述选项。
- 在可用时，将提供的截图、文件、应用捕获、Figma 参考和视觉源材料作为情绪板灵感附加。
- 在可用时，将现有产品截图、类似流程、Storybook 捕获、设计令牌和组件参考作为基础材料附加。
- 当模型数据包含日期或时间敏感信息时，解析确切的当前日期并将其包含在每个图像生成提示中。从该锚点派生可见日期；保留用户或源设计要求的日期。
- 如果截图、图像或视觉文件可用，将实际图像附加到图像生成调用。不要依赖其文本描述。
- 仅当图像生成调用实际收到该图像或可读的本地图像路径时，才声称视觉参考已附加。
- 如果无法附加图像，清楚说明并询问是否继续使用纯文本方向。
- 在每个图像中保留简报的硬性约束。
- 生成选项后，在开始任何构建工作之前停止等待用户选择。
- 当用户稍后选择选项 `N` 时，针对最近一组创意中第 N 张显示的生成图像结果进行解析，而不是原始计划的概念顺序。如果无法确定确切的显示结果，不要基于猜测构建；询问用户命名概念或重新附加/选择图像。
- 选定的选项是 `$image-to-code` 的视觉目标。

## 反馈循环

如果用户在看到选项后给出反馈，用该反馈生成修订选项。

如果用户选择一个选项并给出反馈，在构建之前用该反馈生成一个修订选项。

如果用户喜欢多个选项的部分内容，将这些选择组合成一个新的图像生成设计并在构建之前展示。

## 图像生成提示

调整此提示以适应当前设计简报，附加任何可用的图像参考，并将其发送到图像生成：

```text
创建逼真、生产级质量的 UI 设计，具有清晰的层次结构、强烈的排版、有目的的图像和有目的的间距。

设计一个专注的主屏幕，而不是功能清单。产品可能支持许多工作流，但这个框架应该展示英雄用例、一个清晰的主要操作和仅一两个支持操作或内容区域。不要仅仅为了宣传每个功能而添加卡片、面板、标签页、徽章、指标、筛选器或导航项。让产品的其余部分存在于屏幕之外。优先选择强烈的层次结构和慷慨的留白；如果屏幕感觉拥挤，移除 UI。

### 目标尺寸

选择最匹配用户请求和任何提供的视觉参考的尺寸。

默认使用桌面网页应用框架，除非用户或参考明确要求移动、平板或其他格式。

 - 移动应用：`390 x 844`
 - 平板应用：`834 x 1194`
 - 桌面应用、仪表板、管理后台或 SaaS：`1440 x 1024`
 - 落地页或营销页面：`1440` 宽且可滚动
 - 模态框、面板、小部件或组件：自然容器大小
 - 提供的截图、Figma 框架、模型或参考图像：当用户希望从该视觉继续时，匹配其尺寸和纵横比

为预期界面使用自然的视口比例。永远不要拉伸、挤压或扭曲生成的屏幕、图像、排版或 UI 元素以填充画布。如果构图不能自然适应，请重新构图或简化布局。

避免拥挤。使设计干净地适应所选尺寸，具有真实的间距、可读的类型和没有裁剪的内容。

### 布局

在决定如何在页面上布局元素时，这应该是你用于区分部分的工具优先级顺序：

1. 在同一产品表面上使用间距、分组、对齐、排版和层次结构。
2. 使用简单的分隔线或行分隔符。
3. 仅在基础表面不够时使用微妙的表面色调。
4. 仅在分离仍不清楚时使用边框。
5. 最后使用阴影/ elevation，并且节制使用。

不要：
 - 不要默认使用居中的"应用卡片"（整个 UI 都在页面上的卡片中）位于对比页面背景之上。首先使用基础页面表面，除非源产品或用户明确要求包含的应用面板。
 - 不要在卡片内放卡片。不要将每个主要部分都做成卡片。不要将每个列表项都做成自己的卡片，除非每个项真正是独立的对象。普通列表通常应该读取为一个分组表面，带有轻量级的行分隔。
 - 不要编造无关的功能。只添加对完成原型目标至关重要的事物。不要仅仅为了填充 UI 而编造更多功能。

### 排版

 - 将 UI 排版锚定到可读的产品大小。正文文本通常应位于 14px 到 16px 之间，其余的类型比例围绕该基线构建。
 - 将长文本保持在舒适的行长度，通常每行不超过 65 个字符。
 - 在 UI 中使用不超过 2 种字体。你可以使用项目中可用的任何字体，或 Google Fonts 上提供的免费字体。选择最适合产品目标并与其预期外观和感觉匹配的字体。

### 展示

 - 对于移动应用概念，仅输出应用内容。不要包含设备边框、手机机身、刘海屏、灵动岛、操作系统状态栏、时钟、信号或电池指示器、主屏幕指示器、浏览器外壳、圆角设备遮罩或设备阴影。
 - 不要在单个图像生成中放入多个想法。
 - 在完全遵守给定约束的同时，尽可能变化每个想法。

### 数据新鲜度

当设计包含日期或时间敏感的模型数据时，使用提供的当前日期作为锚点。周视图必须显示真实的包含周，具有正确的工作日/日期对。动态、图表、通知和最近活动必须使用相对于今天的合理时间顺序日期。在有用时标记今天。保留简报或源设计要求的日期。
```

## 输出

等待所有图像生成调用返回后再发送要求用户选择的最终消息。

直到每个请求的生成图像在主聊天中完全可见一次之前，不要发送最终选择消息。

如果可见的图像生成输出比请求的少，重试缺失的生成。不要发送选择消息。

按照对话上下文中出现的顺序为返回的图像生成输出编号：

- 第一个图像生成输出 = 选项 1
- 第二个图像生成输出 = 选项 2
- 第三个图像生成输出 = 选项 3

忽略计划的概念顺序、原始请求链、请求顺序、`Promise.all` 结果顺序、批处理顺序、数组索引、重试顺序和工具提交顺序。

不要命名或描述选项。对于默认的三个图像，仅发送：

`我应该构建哪个选项：1、2 还是 3？或者告诉我你希望先完善或个性化什么。`

仅在用户请求不同数量时调整数字。

如果用户选择了一个数字，在路由到 `$image-to-code` 之前确认所选选项，例如：`正在构建选项 2！` 当映射清楚时不要请求确认。

完成意味着请求的独立图像数量已生成，并且用户已被要求选择一个。
