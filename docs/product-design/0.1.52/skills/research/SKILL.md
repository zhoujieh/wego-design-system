# Research（研究）

为用户指定的产品开展一次全新的 UX 研究扫描。

聚焦当前、有证据支撑的用户问题。优先关注登录后产品体验、自助流程、上手引导、文档/帮助、开发者体验、支持摩擦和产品工作流。

## Critical Overrides（关键覆盖）

- 继续之前先查阅插件路由 [$index](../index/SKILL.md)。
- 遵循 [$critical-overrides](../../references/critical-overrides.md)。

## User Context（用户上下文）

开始前，加载 [$user-context](../user-context/SKILL.md)，并在本地 shell 访问可用时运行其预检脚本。

在相关时，使用已保存的产品链接、Figma 文件、截图、参考图片、代码库路径、Storybook、Token、设计系统、品牌素材、组件引用、浏览器偏好和分享目标作为基础材料。

不要检查每一个已保存的引用。只检查当前任务需要的。

## Contract（约定）

- 在扫描前重述产品、受众、时间范围和研究范围。
- 默认使用公开来源。当连接器可用且用户请求允许时，使用内部来源。
- 尽可能引用来源。
- 将观察到的证据与推断分开。
- 不要从轶事中过度推断。
- 不要返回投诉清单。讲述一个清晰的产品故事。
- 当来源访问缺失或薄弱时，明确说明。

## Workflow（工作流）

1. 重述研究范围。

2. 搜索公开来源：

- Reddit
- X/Twitter
- Hacker News
- Stack Overflow
- GitHub issues/discussions
- 相关论坛、博客、评论、YouTube 评论和开发者社区

3. 在可用时搜索内部来源：

- Slack
- Gong
- Notion
- Google Drive/docs
- Linear/Jira/GitHub
- 如有可用的支持或 CRM 记录

4. 将证据聚类为信号最强的 UX 问题。

5. 区分：

- 产品 UI/工作流摩擦
- 文档/帮助摩擦
- 上手引导摩擦
- 账户、计费、权限或设置摩擦
- 开发者/API/SDK 摩擦
- 可靠性/性能问题
- 功能请求

6. 按严重程度、频率、信心度和产品杠杆对问题进行排序。

7. 讲述一个清晰的产品故事。

## Output（输出）

除非用户要求其他格式，否则默认输出为对话内研究简报。

包含：

- Executive read：用 5-7 句话概括核心故事。
- 排序后的 UX 问题：每个问题包含问题描述、用户目标、页面、失效点、证据、严重程度、频率信号、信心度和建议的产品动作。
- 来源地图：搜索了什么、每个来源的贡献、以及信号薄弱之处。
- 机会地图：将建议按本周修复、本季度修复和需要深入研究分组。

## Rules（规则）

- 尽可能使用引用。
- 不要从轶事中过度推断。
- 将大声抱怨与频繁问题区分开。
- 将 UX 摩擦与缺失功能区分开。
- 将可靠性/性能问题与 UX 工作流问题区分开。
- 将仅限内部的证据与公开证据分开标记。
- 保持简报精炼、具体、易于消化。
