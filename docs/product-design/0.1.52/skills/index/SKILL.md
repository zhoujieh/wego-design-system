# 技能用途

将产品设计请求路由到正确的产品设计技能。将此插件用于 `@Product Design` 提及、直接的产品设计请求，或主要关于设计探索、忠实源克隆、审计、研究、评论或分享的请求。仅仅因为请求提到 UI、原型或视觉风格，并不意味着它是产品设计。

# 插件用途

产品设计插件帮助设计师和其他非编码人员缩小产品创意与工作软件之间的差距。

产品设计插件为你提供以下技能集：

- 研究与产品相关的创意和痛点。
- 进行产品流程审计。
- 使用 ImageGen 为产品生成 distinctly new 的创意。
- 将现有产品应用克隆为轻量级原型。
- 构建轻量级或交互式原型以与团队分享。

## 沟通风格

以温暖、有趣和协作的方式与用户交谈，优先使用简洁的解释而非冗长的文字和大量的项目符号。参考 [communication-protocol](../../references/communication-protocol.md) 以传递产品设计插件的进度更新和移交。

## 关键覆盖规则

- 遵循 [$critical-overrides](../../references/critical-overrides.md)。

## 仅路由

此索引选择下一个产品设计技能。它不做该技能的工作。

如果用户命名了一个专注的技能，首先阅读该确切技能。不要用相关技能替换它。

当请求匹配 `$user-context`、`$get-context`、`$research`、`$ideate`、`$image-to-code`、`$url-to-code`、`$audit`、`$design-qa` 或 `$share` 时，加载专注的技能并遵循它。

对于审计、审查、评论、检查、评估、分析或提供现有产品体验的反馈的请求，直接加载 `$audit`；不要先加载 `$get-context`。如果同一请求还要求之后构建、修复、重新设计或实现，先运行 `$audit`，然后通过适当的正常工作流继续。

对于视觉创意，`$ideate` 是专注的工作流。在 `$ideate` 开始前，使用 `$get-context` 解析最低限度简报并回放任何默认值。

对于实时 URL 的克隆或复现，直接加载 `$url-to-code`。

对于基于 URL 的重新设计、改进或新站点，使用 `$get-context` 确认重新设计简报。`Like <URL>` 意味着重新设计，而不是克隆。使用截图捕获当前站点，将这些截图附加到 `$ideate` 图像生成调用，然后执行 `$ideate`。

## 标准聊天模式

如果产品设计在标准 ChatGPT 聊天中调用，没有工作模式工具，不要启动工作流。一次性告诉用户：

```text
聊天模式不支持产品设计插件。请切换到工作标签页并将此提示粘贴进去以获得完整体验。
```

在用户切换到工作模式之前，不要询问设计简报问题、生成选项或开始构建工作。

## 浏览器选择

在 ChatGPT 工作模式中，始终使用该聊天可用的云浏览器。如果它最初不可见，加载浏览器技能并按照其设置说明操作，然后再断定它不可用。

在 Codex 桌面版中，使用 `@Browser` 并显式选择应用内界面，使用 `agent.browsers.get("iab")`。

在 Codex 桌面版中，仅在用户要求时、任务需要现有的 Chrome 标签页/登录/个人资料/扩展程序，或应用内浏览器不可用或被阻止时使用 Chrome。

如果 ChatGPT 工作模式在预检后未公开云浏览器和 `@Sites`，一次性告诉用户：

```text
云浏览器和 Sites 在此聊天中不可用。我仍然可以构建单页 HTML 原型，但我无法对其进行视觉验证或发布实时检查点，因此保真度和交互打磨可能会较低。继续使用该回退方案吗？
```

仅在用户同意后才继续。不要声称回退方案已验证、已打开、已托管或已准备好分享。此回退适用于图像转代码和新原型。当需要浏览器捕获时，它不适用于 URL 转代码。

## 无视觉目标，不构建

对于没有 URL、截图、Figma 框架、模型、源图像或现有代码目标的新应用、原型、重新设计或 UI 构建请求：

- `$ideate` 是专注的工作流。
- 使用 `$get-context` 解析最低限度简报。
- 一旦目标和预期用户成果清楚，回放假设并在同一轮中运行 `$ideate`。
- 准确展示三个视觉选项，并等待用户选择一个。
- 在选择视觉选项之前，不要搭建、编辑文件或启动服务器。

`完整工作版本`、`无参考`、`继续`、`做出假设` 或完整简报不会放弃此要求。

## 用户上下文

当用户要求以下事项时，使用 [$user-context](../user-context/SKILL.md)：

- 设置产品设计
- 开始使用产品设计
- 使用产品设计入门
- 保存产品或设计源
- 查看产品设计记住的内容
- 更新已保存的产品或设计上下文
- 记住产品设计偏好
- 设置我的插件

调整上下文收集请求以匹配用户的请求。首次设置与更新现有上下文不同。

对于仅设置请求，不要检查工作区、安装依赖、搭建原型、生成图像、运行审计或开始实现。

当回答"你能做什么？"、"如何开始？"或类似宽泛的产品设计问题时，加载 `$user-context` 并在提供已保存上下文入门之前遵循其持久性可用性检查。

在路由到产品设计工作流之前，加载 [$user-context](../user-context/SKILL.md)，并在本地 shell 访问可用时运行其预检脚本。

## 浏览器注释更新

将注释视为对当前原型的范围编辑。

在更改代码之前，阅读注释、其目标和周围屏幕。默认保留现有原型：布局、样式、内容、路由、资源、交互和工作行为保持不变，除非注释要求更改它们。

不要因为注释触及某个区域就重新设计附近的 UI 或重建原型。如果注释不明确且选择会实质性改变原型，请先询问。

## 技能

将此作为产品设计插件工作的根路由指导。如果多个专注技能适用，按创建最有用设计工作流的顺序排列它们。保持此索引作为路由器；不要在此处执行专注工作流逻辑。

### $user-context

预检、保存或从产品设置上下文中回答。在将产品设计工作流路由到这里之前，加载已保存的产品和设计源，以及用于直接设置、入门、保存、记住、回忆、检查或自定义请求。此技能拥有产品设计插件范围内的上下文和偏好策略。

### $get-context

首先将设计、构建、原型制作、重新设计、扩展或 UI 探索工作路由到这里。仅需要清晰的设计目标和预期用户成果。仅当缺失其中之一时才问一个针对性问题；否则回放简报和默认值，然后继续无需等待批准。

### $research

对指定数字产品的当前用户问题进行快速、有来源依据的用户体验研究。将研究用户痛点、用户体验摩擦、入门问题、文档/帮助问题、开发者体验摩擦、支持痛点、产品工作流问题或当前用户投诉的路由到这里。

### $audit

通过截图捕获和审查产品流程、旅程、屏幕或多步骤产品体验。将面向用户的审计、审查、评论、检查、评估、分析或反馈请求路由到这里。它报告与捕获证据相关的用户体验、设计和可访问性发现；不要将 `design-qa` 用于面向用户的审计。

### $ideate

为组件、屏幕、功能、工作流或产品创意生成基于图像的视觉替代方案、混音或概念方向。在 `get-context` 已回放最低限度简报且用户需要视觉探索、设计变体、现有设计的替代方案或想法发现之后，将路由到这里。优先于此纯文本创意，除非用户要求纯文本。

### $url-to-code

使用上述浏览器选择规则将实时 URL 克隆为可运行的仅前端本地应用或网站。当用户提供生产 URL 以进行忠实的本地原型或克隆时，与此一起加载 `get-context`，但直到最低限度简报已回放后才执行它。它不应修改生产代码；当源选择仍不清楚时，保持在 `get-context` 中。

### $image-to-code

将选定的视觉目标实现为忠实的、响应式的、交互式的前端界面。在 `get-context` 已回放最低限度简报且用户已选择图像生成模型、截图、Figma 框架、模型、参考图像或其他视觉源之后，将路由到这里。当未选择视觉目标时，不要从这里开始；先使用 `get-context` 和 `ideate`。

### $share

使用用户首选的目标（如果可用）部署可运行的原型并返回可分享的 URL。当用户要求使用 `@Sites`、`@Vercel` 或其他部署工具分享、部署、发布、托管、创建链接或使原型可分享时，将路由到这里。

### $design-qa

在移交之前，将编码的产品设计原型与其源视觉目标进行比较。仅作为内部助手，在原型、URL 转代码构建或图像转代码构建同时具有源视觉和渲染实现后才路由到这里。不要将广泛的 UX 评论、审计或产品流程审查路由到这里；请改用 `audit`。
