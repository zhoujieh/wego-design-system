# Design QA（设计质量保证）

使用此内部辅助工具，在交接前将原型的源设计与渲染实现进行对比。

不要将此技能用于广泛的 UX 评审、设计评审、产品审计或流程审核。对于这些面向用户的请求，请使用 [audit](../audit/SKILL.md)。

在每次 Product Design 构建交接前使用此技能。

一次通过的 QA 运行需要两者兼备：

- 源视觉目标：Figma 节点、图片、截图、模型或源捕获
- 渲染实现：本地链接、已部署链接、应用屏幕、组件或截图

如果任一产物无法打开、捕获或对比，请编写 `design-qa.md` 并将 `final result` 设为 `blocked`，同时注明阻塞原因。不要让构建技能将其作为已完成交接。

## Workflow（工作流）

以产品质量评审者的身份，将预期设计与实现进行对比，而非作为泛泛的美学评论家。输出必须是一份基于两件产物证据的优先修复清单。

不要仅凭记忆、代码或文件路径编写 QA 评审。先打开或捕获源设计与实现，再对比实际可见的内容。

不要把分开的图片视图假装成并排对比。将源图片与实现截图放在同一个对比输入中，然后从该组合输入中判断可见差异。

设计 QA 是一个迭代循环。仅当首次对比未发现可执行的 P0/P1/P2 差异且未因此进行视觉修复时，方可通过。

当对比发现任何 P0/P1/P2 问题时：

- 记录发现并保持当前结果为阻塞状态。
- 应用修复。
- 在相同的视口和状态下捕获修订后的实现。
- 将修订后的捕获再次与源目标对比。

后续轮次必须识别出之前的发现、已应用的修复以及修复后的视觉证据。构建、依赖、lint、部署和预览故障排查不计入设计 QA 迭代。

1. 确定对比目标。
   - 确定源设计：Figma 节点、图片、设计板、截图、规范或模型。
   - 确定实现：本地链接、已部署链接、应用屏幕、组件、截图或代码渲染视图。
   - 在评判前，确保视口、状态、主题、设备密度、路由、内容、认证状态和交互状态一致。
   - 如果产物不代表相同状态，先明确指出，避免虚假精确。

2. 捕获证据。
   - 对于 Figma，在可用时使用设计上下文和截图工具。
   - 对于 Product Design `mobile-app` 模板实现，捕获应用视口本身，而非整个浏览器页面、桌面画布或周围手机舞台。使用 `data-testid="device-screen"` / `[data-phone-screen]` 进行仅内容对比；仅当源视觉包含设备边框时才使用 `data-testid="phone-frame"`。
   - 在捕获 `mobile-app` 模板前，运行 `npm run check:runtime`。将失败视为阻塞项。不要绕过检查，也不要接受栅格化或重复的状态栏、设备边框或 Home 指示器作为应用内容。
   - 对于 Web/应用实现，遵循 [index](../index/SKILL.md#browser-choice) 中的浏览器选择规则。在 ChatGPT Work Mode 中，在打开本地实现之前，遵循当前构建技能的“在 ChatGPT Work Mode 中预览原型”部分。然后在目标视口捕获截图。
   - 在相关时捕获额外状态：移动端/桌面端、悬停/聚焦/激活、空状态/加载中/错误、深色/浅色，以及关键响应式断点。
   - 在可用时保存截图的路径或 URL，以便发现可以引用证据。
   - 仅捕获截图是不够的。在评判前，将源图片与实现截图放在同一个对比输入中。

3. 在对比前进行标准化。
   - 对齐裁剪、视口大小、缩放和设备框架。不要在没有注明不匹配的情况下，将带框架的模型与无框架的页面进行对比。
   - 优先对比内容区域，而非完整的浏览器外壳或周围画布。
   - 对于 `mobile-app` 模板，在评判保真度前，强制或验证 1:1 的手机屏幕捕获。该模板会将设备缩小以适应较小的浏览器视口；使用足够大的 Playwright 视口以达成 scale `1`，并验证 `[data-phone-screen]` 的测量值为 `393 x 852` CSS 像素。如果屏幕测量值更小，则截图已被缩放，不适合进行 1:1 对比。
   - 使用元素截图或从屏幕元素进行显式剪辑来捕获移动应用，例如：

   ```ts
   const page = await browser.newPage({
     viewport: { width: 1400, height: 1200 },
     deviceScaleFactor: 1,
   });
   await page.goto("http://127.0.0.1:8796");
   const screen = page.getByTestId("device-screen");
   await screen.waitFor({ state: "visible" });

   const box = await screen.boundingBox();
   if (!box || Math.abs(box.width - 393) > 1 || Math.abs(box.height - 852) > 1) {
     throw new Error(`预期未缩放的移动屏幕为 393 x 852，实际为 ${box?.width} x ${box?.height}`);
   }

   await screen.screenshot({ path: "implementation-mobile-screen.png" });
   ```

   - 在对比前标准化图片密度。如果源或实现是 `@2x` 或其他双倍密度，与相同大小的标准化副本进行对比：要么将 `786 x 1704` 的源捕获降采样到 `393 x 852` CSS 目标，要么以相同密度捕获实现并对比相等的像素尺寸。在 `design-qa.md` 中记录源像素、实现像素、CSS 视口和 `deviceScaleFactor`。
   - 不要仅因密度不匹配、浏览器外壳、画布内边距或设备框架不匹配而提交视觉发现。先进行标准化，再评判排版、间距、颜色、图片和状态。

4. 以适当的详细程度进行对比。
   - 使用全视图对比来评判整体构图、层级、布局、密度和响应式结构。
   - 当重要细节在全视图对比中太小无法评判时，使用聚焦区域对比。
   - 从实际的源和实现中选择聚焦区域。在保真度依赖于精确排版、对齐、图像、素材、图标、Logo、控件、表单、导航、表格、密集 UI 或可见交互状态的地方使用它们。
   - 如果不需要聚焦区域，在 `design-qa.md` 中说明原因。
   - 当重要细节无法清晰辨认时，不要仅凭全视图对比就通过 QA。

5. 系统化评审。
   - 当 QA 轮次不只是快速视觉检查时，阅读 [qa-rubric](./references/qa-rubric.md)。
   - 检查信息架构、布局、间距、排版/字体、颜色、图像/图片质量、图标、文案、可供性、交互状态、响应式、可访问性和精细度。
   - 始终对五个必需的保真度表面进行专项检查：字体/排版、间距/布局节奏、颜色/Token、图片质量、文案/内容。即使用户没有明确提到这些区域也要执行。
   - 如果模型没有涉及你看到的某些问题（例如空状态），将其作为模型的不足之处单独记录，需要后续处理。
   - 你的另一个目标是判断实现是否“看起来和模型一样好”。如果存在风格问题，指出来。如果用户的提示泄露到了实现中（而非让应用独立呈现），也指出来。
   - 区分设计漂移与有意的产品/代码约束。如果偏差可能是有意的，将其表述为问题或假设。

6. 产出以修复为导向的 QA 报告。
   - 以发现开头，按严重程度和用户影响排序。
   - 每个发现包含：严重程度、位置、差异内容、证据、重要性原因和具体修复措施。
   - 当实现上下文可用时，包含精确的 CSS/组件/Token 建议。
   - 将客观不匹配与主观优化建议分开。
   - 在检查完必需的保真度表面并明确将剩余差异分类为可接受、预期或仍可执行之前，不要说设计匹配、已完成或已达到最佳效果。
   - 以简洁的实现检查清单结尾。

## Required Fidelity Surfaces（必需的保真度表面）

每份 QA 报告必须明确评估这些表面：

- 字体和排版：族名、后备字体、字重、字号、行高、字距、抗锯齿、层级、换行、截断，以及显示文本和小号 UI 文本是否使用了合适的光学字重。仔细检查字体保真度极其重要，包括查找相似字体或使用图像分析发现字体差异。
- 间距和布局节奏：框架大小、裁剪、对齐、边距、内边距、网格轨道、区块间距、组件间距、圆角、阴影/高度和垂直节奏。
- 颜色和视觉 Token：采样或推断的调色板、渐变、不透明度、对比度、语义状态色、前景/背景平衡，以及 CSS Token 是否映射到源设计。
- 图片质量和素材保真度：主题正确性、裁剪、缩放、清晰度、压缩、透明光晕、遮罩、背景处理、栅格与矢量适用性，以及生成的素材是否匹配源艺术方向。如果视觉目标中的 Logo、插画、装饰标记、产品图片、非标准图标或其他可见图像素材被替换为自定义内联 SVG、手工 SVG、HTML 元素、div/span 形状、CSS 绘制、渐变、emoji、文本字形、占位形状或代码原生近似物，则 QA 失败。
- 应用专属文本的文案和内容

## Severity（严重程度）

- `P0`：阻塞核心使用、严重可访问性失败、布局损坏或不可能完成的任务。
- `P1`：用户可能注意到的主要设计不匹配或可用性退化。
- `P2`：中等视觉漂移、不一致状态、响应式问题或可修复的精细度差距。
- `P3`：提升保真度的细微优化，但不阻塞验收。

将隐藏持久应用控件的视口溢出，以及实质改变首屏内容、主要区域比例、文本换行或界面密度的匹配问题，视为 P2 或更高。

## Output Format（输出格式）

除非用户另有要求，否则使用此结构：

```markdown
**发现**
- [P1] 简短问题标题
  位置：如已知的屏幕/组件/选择器/文件。
  证据：设计是 X，实现是 Y。
  影响：为什么这很重要。
  修复：具体改动。

**待澄清问题**
- 关于有意偏差、不可用状态或缺失产物的任何模糊之处。

**实现检查清单**
- 可直接执行的有序修复。

**后续优化**
- 交接后可提升保真度的 P3 优化。
```

如果没有实质性不匹配，清楚说明并列出任何残留的测试缺口。

当此技能在交接前使用时，将最新 QA 报告保存为项目根目录的 `design-qa.md`。

`design-qa.md` 必须包含：

- 源视觉真值路径
- 实现截图路径
- 视口
- 源和实现的像素尺寸、CSS 大小和使用的密度标准化
- 状态
- 全视图对比证据
- 聚焦区域对比证据，或为什么不需要
- 发现
- 每次 P0/P1/P2 迭代的对比历史：之前的发现、已应用的修复和修复后的视觉证据
- 最终结果

对于 ChatGPT Work Mode 构建，`design-qa.md` 必须包含浏览器渲染的实现截图、视口、测试的主要交互、检查的控制台错误和最终结果。如果缺少浏览器渲染证据，`final result` 为 `blocked`。

`final result` 必须恰好是 `passed` 或 `blocked`。

当没有可执行的 P0/P1/P2 发现时使用 `passed`。P3 发现可作为后续优化保留。

当存在可执行的 P0/P1/P2 发现时，使用 `blocked` 并指明阻塞原因。

返回 QA 报告的文件路径。
