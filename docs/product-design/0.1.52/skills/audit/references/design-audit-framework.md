# 设计审计框架

将此结构用于 `audit`。

将 `audit` 用于对更广泛体验的系统评估，而非对单个工件的反馈。

## 审计模式

- `用户体验审计`
- `可访问性审计`
- `组合审计`

## 用户体验审计视角

- 任务入口和可发现性
- 信息架构
- 交互流程和摩擦
- 层次结构和清晰度
- 信任和 reassurance
- 默认状态和空状态
- 文案和号召性用语
- 跨体验的一致性

## 可访问性审计视角

- 可感知的内容和对比度风险
- 语义结构和阅读顺序
- 键盘访问和焦点行为
- 目标大小和交互 affordances
- 标签、说明和错误恢复
- 运动、计时和状态变化沟通
- 响应式重排和缩放弹性
- 辅助技术清晰度和鲁棒性

## 用户体验审计输出结构

1. `审计范围`
2. `用户目标`
3. `优势`
4. `显著风险`
5. `机会领域`
6. `可选比较上下文`
7. `建议`

## 可访问性审计输出结构

1. `审计范围`
2. `可访问性目标`
3. `已确认的优势`
4. `可能的问题`
5. `WCAG 相关考虑`
6. `证据限制和验证差距`
7. `建议`

## 组合审计输出结构

1. `审计范围`
2. `用户目标和可访问性目标`
3. `优势`
4. `用户体验风险`
5. `可访问性风险`
6. `机会领域`
7. `证据限制和验证差距`
8. `建议`

## 护栏

- 关注体验模式，而非业务策略。
- 比较产品保持可选；仅当它们使审计更清晰时才使用。
- 将结构性问题与打磨问题分开。
- 将建议与用户目标、工作流或可访问性结果联系起来。
- 除非用户提供了支持该声明所需的实现细节，否则不要暗示完整的 WCAG 合规性。
- 如果请求是关于单个屏幕、组件、模态框或有界交互的，将审计范围限定到该界面。
