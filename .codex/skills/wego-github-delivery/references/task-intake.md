# 新任务启动清单

> 所有新任务（业务原型、设计系统维护、工作流维护）开工前必须按本清单执行。
> 目的：防止同一任务被重复建分支、防止跳过需求确认、防止环境残留。

## 第 0 步：判断会话上下文

先判断当前是否已有活跃的任务上下文：

- **有上下文**：当前在任务 worktree 中（非主 worktree），且存在未冻结的业务迭代，或存在非业务任务的活跃功能分支。
- **无上下文**：在主 worktree / main 分支，没有活跃迭代或功能分支。

```
有上下文吗？
├─ 无 → 走完整启动（第 1~5 步）
└─ 有 → 新需求属于当前上下文吗？
     ├─ 属于（同一场景、同一业务目标的延伸）→ 跳过启动，直接继续
     └─ 不属于（换场景、换业务目标）→ 走轻量启动（第 1、3~5 步，跳过第 2 步）
```

**"属于当前上下文"的判断标准**：同一场景 + 同一业务目标（迭代 ID 不变）。不同场景或不同业务目标 = 独立交付单元。

## 第 1 步：分支巡检（完整与轻量启动都执行）

> 目的：闭合"PR 合并后本地分支残留"的收口缺口。PR 合并是异步发生的（网页端合并 / CI 自动合并），
> 远端分支被 GitHub 自动删除后，本地分支若无收口机制会长期残留，必须每次启动巡检收口。

1. 用 `git branch -vv` + `npm run branches:stale` 巡检全部本地分支：
   - 已合入 main（tip 是 main 祖先）或上游已删且内容与 main 一致的分支 → 收口删除：`npm run branches:prune`；上游已删（gone）类需确认内容已进 main 后用 `npm run branches:prune-gone`。
   - 有 worktree 检出、有开放 PR、或无法归属的分支 → 保留，或先关联到交付单元/确认废弃，不得长期静默保留。
2. 巡检结果与当前交付单元冲突时，先确认归属再处理。
3. 中断兜底：若待接手/待清理 worktree 的 `.tasks/experience-inbox.json` 留有未处理草稿，交 `wego-uxsystem-iterate` 补做经验收口后再继续，不得直接清理 worktree。

## 第 2 步：环境同步与清理（仅完整启动）

1. 主 worktree 执行 `git pull --rebase origin main`。
2. 会话前置读取 `.codex/skills/wego-uxsystem-iterate/experience/EXPERIENCE.md` 核心摘要（轻量启动且本会话已读过则不重复读）；命中场景技能挂载点时再按需读取对应 `wego-scene-*`。
3. 检查是否有带 `needs-sync` 标签的开放 PR（CI 自动同步 main 时冲突会打此标签），有则先处理冲突。
4. 检查 `.tasks/preview-servers/` 中的预览服务记录：
   - 进程已失效、worktree 已不存在、记录分支与实际分支不一致、或 PR 已关闭/合并 → 停止进程并删除记录。
   - 仍在本地迭代或等待合并的服务 → 保留，不得清理。

## 第 3 步：交付单元核对

### 业务原型任务

运行：

```bash
node scripts/resolve-delivery-unit.mjs --scene {场景}
```

结果处理：

- **matched**：接手结果指定的分支、worktree 和可选开放 PR。已确认范围内的反馈留在原迭代中处理；只有改变业务事实时才回到 wego-product 更新简报。
- **new**：确认无匹配后，才允许创建新迭代和新分支。
- **conflict**：多个候选或无法完成必要核对 → 停止并说明阻塞原因，不得自行选择候选。

**人工兜底（必须执行）**：核对返回 `new` 后，再用 `git branch -vv` 扫一遍所有分支，检查是否有同场景或相关场景的悬空分支（无 worktree 但分支存在）。有则先确认是否为同一任务，是则恢复 worktree 而不是新建。

### 非业务任务（设计系统维护、工作流维护）

`resolve-delivery-unit.mjs` 不适用（无场景参数）。直接判断：

- 是否已有同一目标权威源的开放 PR 或功能分支？有则复用，无则新建。
- 不需要创建业务迭代。

## 第 4 步：需求规格确认（仅业务原型新需求或范围变化）

- **matched + 范围未变** → 跳过此步，直接进入 wego-design。
- **matched + 范围变化** → 进入 wego-product，在原迭代中失效简报、更新需求规格说明、重新提交并确认。
- **new** → 进入 wego-product，init 迭代 → 写 spec.md → submit-brief → 用户确认后 confirm-brief。

**两次确认的边界**：
- 立项确认（第 0 步前的读代码与用户沟通）：判断要不要做、做哪个场景、大致范围。
- 规格确认（本步）：细化目标、入口、关键路径、状态、数据契约。

## 第 5 步：工作环境就绪

- **new**：从最新 `origin/main` 创建 `feature/<owner>-<task>` 分支 + 独立 worktree（`git worktree add ../<owner>-<task> -b <分支>`）。
- **matched**：切换到已有 worktree，确认当前分支与任务分支一致。
- 确认 worktree 中无未提交的游离改动（归属不清的先交由用户确认保留或还原）。

## 第 6 步：进入对应技能执行

- 业务原型 → wego-design（或 wego-product 如果还在需求阶段）
- 设计系统维护 / 工作流维护 → wego-uxsystem-iterate

## 轻量启动 vs 完整启动

| 步骤 | 完整启动（新会话/无上下文） | 轻量启动（有上下文/切换任务） |
| --- | --- | --- |
| 第 0 步 上下文判断 | ✅ | ✅ |
| 第 1 步 分支巡检 | ✅ | ✅ |
| 第 2 步 环境同步与清理 | ✅ | ❌（除非距上次已超过合理时间或 main 有新合并） |
| 第 3 步 交付单元核对 | ✅ | ✅ |
| 第 4 步 需求规格确认 | 按需 | 按需 |
| 第 5 步 工作环境就绪 | ✅ | ✅（切换 worktree） |
| 第 6 步 进入技能 | ✅ | ✅ |

## 同一会话多交付单元规则

- 一个会话可以同时有多个活跃交付单元（各自独立 worktree），但每次只能在一个 worktree 中操作。
- 切换交付单元时走轻量启动（第 1、3~5 步）。
- 预览服务端口不得冲突；同一交付单元复用已有服务，不同交付单元使用不同端口。
