# 交互原型设计方法

> 角色：`wego-design` 在已确认 `prototype_brief` 之后、读取具体组件 Preview 之前执行的唯一页面设计流程。本文决定“如何形成页面方案”；业务事实由简报提供，精确组件结构由 Preview 与组件契约提供。

## 1. 设计授权与边界

<!-- rule-id: confirmed-brief-is-design-authorization -->

有效迭代中已确认的 `prototype_brief` 即本轮交互原型的设计与实现授权。`wego-design` 在已确认范围内自行决定信息分组、页面结构、组件选择、视觉层级、间距、颜色 Token、反馈方式和 overlay 形式，不因这些设计细节再次要求用户确认。

以下情况才退回 `wego-product`：

- 缺少或冲突的业务事实会改变目标、范围、入口、关键路径、状态、数据含义或完成结果。
- 设计系统无法支持已确认的产品阶段交互视觉描述，需要用户确认业务替代方案。
- 可选方案会改变不可逆行为、业务风险、流程连续性或用户最终得到的结果。

不从 UI Kit、组件、历史场景、临时线框或设计偏好补造业务事实。产品阶段已经确认的交互视觉描述是强约束；未明确的设计细节由 `wego-design` 负责完成。

## 2. 先形成设计意图

<!-- rule-id: design-before-component-consumption -->

读取共享设计决策原则和设计消费边界后，先在当前任务上下文中形成以下临时设计模型，再读取具体组件 Preview：

- **业务时刻**：用户为什么此刻来到页面。
- **首要任务**：本页唯一必须优先完成的事。
- **核心对象**：页面围绕什么人、内容、商品、数据或配置展开。
- **持续主行动**：推动任务完成且需要持续可见的操作；没有则明确为无。
- **辅助信息与次级入口**：哪些内容用于判断，哪些只在需要时出现。
- **必要可见状态**：简报要求或真实操作必然产生的状态与反馈。
- **首屏承诺**：用户进入首屏后应立即看懂“这里是什么、现在怎样、下一步做什么”中的哪些内容。

该模型只用于生成过程，不新增文件、合同字段或用户确认节点。无法从已确认简报得到其中的业务事实时，按第 1 节退回；能够由设计原则裁决的结构和视觉问题不得上抛给用户。

## 3. 选择精确范式或自主组合

<!-- rule-id: exact-pattern-or-composed -->

用业务任务、surface 角色、状态形态和交互模式逐项匹配 `uikit-plan.json.pagePatterns`：

- 全部满足某个范式的 `appliesWhen`，且不命中 `excludeWhen` 时，使用 `pattern`，只读取该范式对应的 UI Kit、presentation 和候选组件。
- 没有精确命中时，使用 `composed`。不得选择“最接近”的 UI Kit，不得拼接多个 UI Kit，不得复制 UI Kit 页面壳、演示布局或业务文案。
- `composed` 不是自由拼凑。它必须先根据设计意图建立语义区域，再为区域匹配正式组件。

UI Kit 只证明某个明确页面范式如何组合正式能力，不负责替 AI 完成页面设计。未命中范式本身不是设计系统缺口。

## 4. 建立语义区域树与页面布局合同

在选择具体组件前，按本页实际需要从以下区域中取舍并排序：

1. 上下文与身份：返回、标题、对象身份、当前范围。
2. 首要工作区：完成首要任务所需的核心内容或控件。
3. 辅助摘要：帮助判断但不应抢夺焦点的信息。
4. 次级导航：筛选、切换、更多入口或下钻关系。
5. 持续主行动：固定操作栏或模态操作区中的唯一主行动。
6. 浮层与反馈：按需出现的选择、确认、结果或异常恢复。

每个区域必须能回答“它如何服务首要任务”；无法回答的区域删除、合并、降级或延后。先确定区域顺序、父子关系、滚动边界、固定区域和信息显隐，再进入组件映射；禁止从组件索引反推页面布局。

读取 `page-layers.json` 后，必须在 `layout_contract` 中同时完成四部分：

- `page_layers`：每个页面区域属于哪个 scope/role，页面内导航、吸顶与固定操作统一使用 `page-local/navigation`。
- `scroll_architecture`：唯一主滚动区、必要的嵌套滚动区、固定区域及其安全区/内容避让责任。页面根与主滚动区必须通栏；滚动底部避让统一消费 `library-consumption.json#/layoutContract/scrollBottomRule`。
- `layout_groups`：按内容语义成组声明横向边距和垂直节奏，同一组只有一个 `spacing_owner`；不得按组件类型分组，也不得用页面根统一设置内容边距。
- `sticky_regions`：登记吸附边缘、显隐策略、层级、不透明背景、底部间距和滚动避让方式。navbar、保存、结算和高优先级告警不得使用自动隐藏策略。

Sticky surface 和 bottom action surface 必须通栏并有明确背景；其内部控件留白由组件内层承担。顶部吸顶区使用动态实测高度维护 `scroll-padding-top`；底部避让按 `scrollBottomRule` 登记、实现和验证，不在本方法中维护第二份数值或公式。

## 5. 复杂页面才生成两个结构候选

<!-- rule-id: complex-page-two-structure-alternatives -->

满足以下任一条件时，在任务上下文中生成两个有实质差异的结构候选：

- 存在多个看似合理的首要任务。
- 顶层语义区域超过 4 个。
- 同页存在 2 个及以上独立的导航或切换轴。
- 存在多个可能需要持续可见的主行动。
- 辅助信息与首要工作区争夺首屏。
- 未命中页面范式，且需要混合列表、表单、总览等不同结构。

简单、成熟、精确命中范式的页面直接形成一个方案，不机械生成候选。候选只比较结构策略，例如“任务优先、摘要后置”和“摘要先行、任务下钻”；不得仅通过换颜色、圆角或装饰制造伪差异。

按“清晰 > 高效 > 一致 > 美观”选择最终方案，至少说明：

- 首要任务为何最清楚。
- 关键路径是否更短、更连续。
- 哪些信息被保留、降级或按需显示。
- 滚动、固定操作和返回关系是否稳定。

候选不新增持久化产物；最终理由写入现有 `layout_contract.selection_reason`，相关视觉语义写入现有 `token_bindings.content_role`。

## 6. 结构确定后映射正式组件

语义区域树确定后，才建立本页组件计划：

1. 用组件索引为每个区域定位候选组件，不扫描全库寻找“看起来能拼”的东西。
2. 逐个读取本页命中组件的 Preview，再读对应契约。
3. 根据 Preview 的代表变体确认 DOM、class、状态与可选节点，组件结构逐字复制。
4. 组件约束若使原结构不可成立，回到语义区域树调整结构；不得用场景 CSS 重造或包裹出等价组件。
5. 正式能力确实无法覆盖时，选择可用正式回退并记录最小缺口，不在业务场景发明组件。

overlay 形式由当前任务、内容量、风险、流程连续性、关闭与恢复方式共同决定；只有它会改变业务结果或已确认产品指令时才退回产品阶段。

## 7. 分配视觉语义并实现

组件映射后再分配 Token 和场景布局：

- 标题、对象名称、正文、字段值、说明、元数据和状态必须使用明确的内容角色。
- 中性色承载内容，品牌色只强化主行动，状态色只表达对应状态。
- 场景样式只负责区域关系、语义内容组间距、滚动与业务胶水；页面根和主滚动区不承担内容边距，组件内部视觉由正式组件负责。
- 用留白、分组、层级和显隐建立秩序，不靠堆叠卡片、彩色底板、阴影或装饰图标制造“设计感”。

实现必须遵循场景合同，且不得在实现过程中把已经裁决的结构悄悄改成更容易编码的布局。

## 8. 实现后完成一轮设计自审

<!-- rule-id: prototype-design-self-review -->

实现完成后、进入测试与交付前，必须基于实际页面进行一轮设计自审：

- 首屏能否识别页面上下文、当前状态和唯一下一步。
- 页面是否仍只有一个首要任务，辅助信息是否抢夺焦点。
- 信息分组、滚动边界、固定操作和返回关系是否符合最终结构方案。
- 每个可见组件是否服务某个语义区域，是否出现因“库里有”而加入的元素。
- 内容角色、视觉层级、密度和间距是否形成稳定节奏。
- 空、错、处理中和完成反馈是否延续同一任务上下文。

发现问题时只允许完成一轮有明确理由的设计修订，然后再进入既有提取、合同、交互和视觉检查链路。自审不是新增测试门禁，不新增合同 Schema，也不要求为所有页面迁移历史产物。

## 适用边界

- **applies_when**：有效迭代中已有用户确认的 `prototype_brief`，需要新建或修改用户可见业务场景。
- **avoid_when**：仅修改组件、Token、Preview、UI Kit、守卫或设计系统源；此时使用 `wego-uxsystem-iterate`。
- **exceptions**：用户明确确认的产品阶段交互视觉描述必须遵循；与正式设计系统冲突时按第 1 节退回，不由设计阶段静默替换。
- **fallback**：精确命中页面范式则使用 `pattern`；未命中一律使用 `composed` 的语义区域流程；正式组件能力不足时使用可用正式回退并提交最小缺口说明。
