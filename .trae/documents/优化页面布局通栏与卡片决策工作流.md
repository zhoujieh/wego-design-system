# 优化页面布局通栏/卡片决策与移动端横向 padding 工作流

> 本轮为 **工作流迭代模式**（wego-uxsystem-iterate），基于"价格管理"任务暴露的问题优化工作流规则。
> 范围：只改工作流约束文件（uikit-plan.json / SKILL.md / specs / wego-tests 验收），**不改生成产物**（价格权限管理 scene.css / scene.js 保持现状）。
> 遵循 `references/workflow-iteration.md` 四段式经验沉淀：工作流环节归属 → 场景类型识别 → 判断条件定义 → 决策动作落地。

## 一、问题与根因分析

### 问题 1：页面布局默认都按卡片布局输出了

**现象**：价格权限管理 scene 的 `scene.js` 中 3 处 `cell-group__content cell-group__content--card`（行 106、173、199），`scene.css` 第 28 行 `.price-list-body / .price-perm-body` 用了 `padding: var(--spacer-12) var(--spacer-12) ...`（横向 12px）。

**根因**：
- `uikit-plan.json` biz-rule-config 的 `structureHighlights[4]` 写的是条件式规则："连续 cell/form 分组是否开启卡片修饰，**取决于** phone-body 或等价宿主内容层是否承担横向留白"——没有指定默认方向。
- `compositionConstraints[4]` 同样写"当宿主内容层承担横向留白时，仅在 content 容器上开启卡片修饰类"——AI 倾向于"先给 phone-body 加横向 padding，再开 --card 修饰"，从而**默认走卡片模式**。
- `wego-design/SKILL.md` 对 `layout_pattern` 输出要求只写了"内容布局类型"，没有要求显式声明"通栏/卡片"模式，导致 AI 用 `cell-group__content[+--card]` 这种条件性记法模糊带过。

### 问题 2：命中 biz-rule-config uikit 的页面没有严格按通栏模式输出

**现象**：同问题 1，命中 biz-rule-config 的价格权限管理页面应该按通栏模式（phone-body 0 横向 padding + cell-group__content 无 --card）输出，实际却走了卡片模式。

**根因**：
- `ui_kits/biz-rule-config/index.html` 的 `BizSettingsContent`（模态屏）明确示范了通栏模式：`.phone-body` 无横向 padding，`.cell-group__content` 无 `--card` 修饰，cell 横向边距由 `.cell__body` 自带 16px padding 承担。
- 但 `uikit-plan.json` 没有把这条 UI Kit 范式固化为结构化约束，`compositionConstraints` 中没有"biz-rule-config 命中页面默认通栏"的硬约束。
- AI 看到 `structureHighlights[4]` 的条件式描述，默认选择"给 phone-body 加 padding + 开 --card"的卡片路径，破坏了 UI Kit 范式。

### 问题 3：移动端 scene 页面内容左右边距视觉变小（用户描述"变为0"）

**现象**：用户反馈移动端"我的"tab 下钻打开的页面（如价格管理）内容左右边距视觉变小，接近"0"。

**根因（经 search agent 全量 CSS 审查确认）**：
- **不是 CSS bug**：`wego-app/css/app.css` 第 73 行 `.host-shell-page` 横向 padding 是 `var(--spacer-16)` = 16px，桌面/移动一致，移动端 media query 未覆盖。
- **真正根因是工作流决策问题**：
  1. 价格权限管理 `scene.css` 第 28 行自决策 `padding: var(--spacer-12) var(--spacer-12) ...`（横向 12px），**既不是 M1（0px）也不是 M2（16px）**，违反 `specs/布局与间距规范.md#页面边距` 的 4N 规则和 M1/M2/M3 三档规范。
  2. `design_consumption_plan.json` 的 `allowed_page_styles` 只写了模糊描述："页面外层 phone-body 间距（gap: var(--spacer-8), padding-bottom 安全区）"——没有声明横向 padding 的具体值和模式（M1/M2）。
  3. **桌面端视觉缓冲掩盖了问题**：桌面端 phone-frame 有 8px border + preview-shell 16px padding，加上 scene body 12px，总视觉留白 36px，看起来"还行"。
  4. **移动端视觉缓冲消失暴露问题**：移动端 phone-frame border: none + preview-shell padding: 0，只剩 scene body 12px，视觉上从 36px 骤降到 12px，用户感受为"边距变小/变为0"。
- **附加影响因素**：`wego-app/css/app.css` 第 188-191 行 `.host-shell-app-card__content, .host-shell-list-card__content { padding: 0 }` 是易误解规则（设计意图是让 grid/cell__body 自带 padding 承担边距，但 AI 读取时可能误以为"card content padding: 0 = 页面边距为 0"）。这条规则本身正确，不在本轮修改范围，但需要在工作流中加注释约束防止 AI 模仿。

## 二、四段式经验沉淀

### 2.1 工作流环节归属

| 问题 | 归属环节 | 落地文件 |
|------|----------|----------|
| 问题 1（默认卡片） | wego-design（pagePattern 约束不明确） | `uikit-plan.json`、`wego-design/SKILL.md` |
| 问题 2（biz-rule-config 应通栏） | wego-design（UI Kit 范式未固化为约束） | `uikit-plan.json` |
| 问题 3（移动端横向 padding 视觉变小） | wego-design（allowed_page_styles 模糊）+ wego-tests（验收缺项） | `wego-design/SKILL.md`、`wego-tests/references/` |

### 2.2 场景类型识别

本轮注册/强化的场景类型：**page-layout-mode-decision**（页面布局模式决策）

- 触发条件：生成 `design_consumption_plan.json` 时，需要为每个 `surface_designs[].component_mapping` 决定页面布局模式（通栏 M1 / 卡片 M2）。
- 决策依据：
  - 命中 `biz-rule-config` pagePattern 的 surface → 默认通栏 M1
  - `host-entry` surface（宿主入口列表）→ 卡片 M2
  - 其他 fallback blueprint surface → 默认卡片 M2，除非业务语义明确是通栏内容（如全屏图片浏览）

### 2.3 判断条件定义

判断条件必须是**结构特征/语义特征/宿主特征**，不能是"组件名+修饰类名"（遵循 `workflow-iteration.md` 经验沉淀通用化原则）：

| 判断条件 | 决策动作 |
|----------|----------|
| 语义特征：surface 命中 `biz-rule-config` pagePattern（业务规则配置、权限管理、库存规则等） | 默认通栏 M1：phone-body 0px 横向 padding + cell-group__content 无 --card 修饰 |
| 宿主特征：surface 角色为 `host-entry`（宿主入口列表，承接 grid/cell 入口） | 卡片 M2：phone-body 16px 横向 padding + cell-group__content--card 修饰 |
| 结构特征：surface 为连续 cell/form 分组且宿主层不提供横向留白（biz-rule-config 默认场景） | 通栏 M1：由 cell__body / form-body 自带 16px padding 承担内容横向边距 |
| 结构特征：surface 为连续 cell/form 分组且宿主层明确提供横向留白（host-entry 场景） | 卡片 M2：cell-group__content 开 --card 修饰 |

### 2.4 决策动作落地

`design_consumption_plan.json` 的 `layout_pattern` 字段必须显式声明模式：

```json
"layout_pattern": "通栏模式 M1：phone-body 纵向流（0px 横向 padding）+ cell-group 分组（cell-group__title + cell-group__content 无 --card）承接连续 cell；cell 横向边距由 cell__body 自带 16px padding 承担"
```

或

```json
"layout_pattern": "卡片模式 M2：phone-body 纵向流（16px 横向 padding）+ cell-group 分组（cell-group__title + cell-group__content--card）承接连续 cell"
```

**禁止**使用 `[+--card]` 这种条件性记法，必须明确写出"通栏模式 M1"或"卡片模式 M2"。

## 四、假设与决策

### 假设
1. 用户描述的"我的 tab 页面内容左右边距变为0"指的是从"我的"tab 下钻打开的 scene 页面（如价格管理），而不是宿主 wego-app/index.html 的"我的"tab 本身。宿主"我的"tab 的 `.host-shell-page` 横向 padding 是 16px，桌面/移动一致，无 CSS bug（经 search agent 全量审查确认）。
2. 用户说"不需要改生成产物"，所以价格权限管理 scene.css/scene.js 保持现状，本轮只优化工作流约束。
3. `wego-app/css/app.css` 第 188-191 行 `.host-shell-app-card__content, .host-shell-list-card__content { padding: 0 }` 是设计系统本体规则，本身正确（让 grid/cell__body 自带 padding 承担边距），不在本轮修改范围。但会在 wego-design SKILL.md 中加约束，防止 AI 在 scene.css 中模仿此写法覆盖宿主横向 padding。

### 决策
1. **不修改 cell.json / form.json 的 usageHints**：原规则"取决于宿主是否承担横向留白"本身没错，只是不够指令性。本轮通过在 uikit-plan.json 中新增 compositionConstraints[6] 来明确默认方向，不改动组件契约文件。
2. **不修改 wego-app/css/app.css**：宿主壳 CSS 没有 bug，不调整。app.css 第 188-191 行的 `padding: 0` 规则保留，但通过工作流约束防止 AI 模仿。
3. **版本递增 306→307**：因为修改了 uikit-plan.json 的 pagePattern 约束和 specs，属于设计系统本体迭代。
4. **不回流到 AGENTS.md**：本轮规则只影响 wego-design 工作流环节，不升级为仓库级硬约束（不写入 AGENTS.md 的"仓库级约束"章节）。
